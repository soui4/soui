## 1. 线程模型与安全目标

### 1.1 SOUI 的线程原则

**同一个窗口树（SHostWnd 及其全部 SWindow 子孙）在任一时刻只允许一个 UI 线程访问。** 一个应用可以有多个 UI 线程，每个线程运行自己的消息循环（`SApplication::AddMsgLoop` 按 `GetCurrentThreadId()` 注册），并拥有各自创建的窗口树。SOUI 不在 SWindow 内部加锁——窗口树内数据的互斥靠"线程亲和性"约定保证，而不是靠锁。

由此得出两层并发模型：

| 层级 | 对象 | 并发策略 |
|---|---|---|
| 窗口树 | SWindow / 控件 / 它们的绘制 RT | 单线程亲和，无锁；跨线程操作必须封送 |
| 全局共享 | skin 对象、资源池、工厂、渲染后端、通知中心 | 多 UI 线程并发调用，框架内部负责同步 |

### 1.2 合法的跨线程通道

窗口树之外的数据进入某个 UI 线程，只有三条合法通道：

1. **Win32 消息**：对 host HWND `::PostMessage`/`::SendMessage`，由操作系统封送到窗口所属线程。
2. **任务投递**：`IMessageLoop::PostTask` / `ITaskLoop::postTask` / `STaskHelper::post`。**禁止按值传递 `SStringT`**（见 §5.2）。
3. **异步事件**：`SNotifyCenter::FireEventAsync`，由主线程的 `SNotifyReceiver` 定时器统一派发。

### 1.3 共享对象的安全目标

skin 等共享对象的目标是 **"多 UI 线程共享时不崩溃"**，而不是"各线程看到独立的数据"。允许的代价包括：绘制期间观察到半染色像素、读到的颜色/帧号瞬时撕裂（对齐 POD 读写在硬件层面不会崩溃）；不允许的是悬空指针、引用计数错乱和容器损坏。

## 3. skin 对象线程安全设计（skinobj 专项）

### 3.1 设计前提

1. 目标是**不崩溃**，不追求线程间数据独立；接受像素级撕裂。
2. **lazyLoad 必须保留**（防止启动时集中加载所有资源）。
3. SVG 的 scale 缩放副本**共享同一个 `ISvgObj`**（对副本染色同步影响原 skin 属预期行为）。
4. 所有 skin 初始化后**只读为主**，改写是少数场景（染色、换源）。

### 3.2 锁模型（SSkinObjBase.h 中有权威注释）

每个 skin 对象一把 `mutable SCriticalSection m_cs`（**递归**），四条规则：

1. **初始化只发生一次**：XML 解析、`SetImage`/`SetSvg`、首绘懒加载，之后长期只读。
2. **懒加载与缓存填充在锁内执行**；对外以 `SAutoRefPtr<T>` 返回引用，在途绘制持有对象不被提前释放。
3. **`OnColorize` 原地改像素**（锁内）：位图/SVG 对象身份永远不变，并发绘制持有的指针恒定有效，最坏观察到半染色像素——与"不崩溃优先"的前提一致。
4. **`Scale()` 入口一次加锁**覆盖"读源 + 写副本"全程，各 `_Scale` 实现零锁代码；递归锁保证 `_Scale` 内可安全调用加锁的 getter。

### 3.3 关键接口约定

| 接口 | 返回类型 | 语义 |
|---|---|---|
| `GetImage()` / `GetSvg()` | `SAutoRefPtr<T>` | 锁内懒加载 + AddRef；赋给裸指针仍兼容（隐式转换，借出语义） |
| `GetDrawable(pImg, pSvg)` | 引用出参 | **绘制路径唯一入口**：一把锁一次拿齐两个引用，绘制全程不再碰锁 |
| `GetSvgCacheBitmap()` | `SAutoRefPtr<IBitmapS>` | 锁内查/填 SVG 光栅缓存；染色重置换 NULL 时在途绘制持引用不 UAF |
| `SetImage` / `SetSvg` / `OnAttrSrc` | — | 全部加锁；运行期换源安全，旧对象由在途绘制保活 |

### 3.4 当前实现核验结果

- 四条绘制路径（`SSkinImgList`/`SSkinImgCenter`/`SSkinImgFrame`/`SSkinScrollbar`）已统一走 `GetDrawable`，全程持有引用，核验无裸指针残留。
- `SSkinButton::OnColorize` 已加锁（`6a07fd14`）；`_DrawByIndex` 读 `m_colors` 无锁——POD 撕裂不崩溃，符合前提。
- 全部 `_Scale` 实现（基类、ImgList、ImgFrame、SSkinAni、SSkinNewScrollbar、SCard）核验**均未重入 GETSKIN**，不构成锁序反置。
- lazyLoad 属性已恢复并纳入 `GetDrawable` 锁内路径，`games/upgrade` 的 `SCard` 同步兼容。

## 4. skin 池与 SUiDef：单一锁

`SSkinPool` 自身**无锁**。全部公共 API（`GetSkin`/`AddSkin`/`RemoveSkin`/`RemoveAll`/`_LoadSkin` 插入段）通过 `CSkinLock` RAII guard 串行到 `SUiDef::GetSkinLock()`（递归 CRITICAL_SECTION），与 SUiDef 的 skin/style/font 查找共用同一把锁。

**收益**：

1. pool 与 SUiDef 之间的 ABBA 死锁**结构性消失**——只有一把锁，无需锁序推理；`GetSkin` 内按需 `Scale()` 变成合法的同线程递归。
2. 外部直调池 API 自动安全。真实调用点已核实：`controls.extend/SImagePlayer.cpp`（gif 首播时向内置池推 skin）。
3. 锁序收敛为唯一一条：`SUiDef 锁 → skin m_cs`。`GETUIDEF` 判空降级为 no-op，覆盖 shutdown 后的边缘调用。

**已固化的硬约束**（写在 `SSkinPool.h` 注释中）：**skin 自身的 `m_cs` 被持有期间禁止调用 `GETSKIN`/`SUiDef::GetSkin`**。线程 A 持 skin X 的 `m_cs` 等 SUiDef 锁、线程 B 持 SUiDef 锁（`SSkinPool::GetSkin`）等 X 的 `m_cs`（`Scale()` 入口）即构成 ABBA。当前代码合规，新增复合 skin 时必须遵守。

## 5. 已知风险与约束（评价）

### 5.1 约定级安全点（依赖"启动期单线程"）

- `SObjectFactoryMgr::RegisterFactory`（skin/控件/渲染工厂注册）、`SNamedID`、`SObjDefAttr`、`SetDefFontInfo` 均无锁，依赖启动期单线程注册后只读。运行期重注册会与 `CreateObject` 竞争。
- `SLog::setLogCallback`：源码注释已声明非线程安全，仅限程序启动时调用。

### 5.2 SStringW 跨线程按值传递

`TStringData::AddRef` 为**裸 `nRefs++`**（非原子）。COW 语义下两个线程共享同一字符串缓冲区时，并发 AddRef/Release 会造成计数错乱 → 双重释放。因此：

- 跨线程任务投递（PostTask 等）**禁止按值捕获 `SStringT`**，lambda 只捕 `this` + POD 或改用堆拷贝。
- 窗口消息携带字符串须用堆分配/静态缓冲，并在接收方接管生命周期。

### 5.3 GETSKIN 借出指针窗口

`SSkinPool::GetSkin` 返回池内裸指针（引用归池所有），调用方赋给 `SAutoRefPtr` 时才真正 AddRef。若运行期另一线程 `RemoveSkin`/`RemoveAll` 恰在"返回之后、AddRef 之前"释放了该 skin，即 UAF。当前池的增删只发生在启动加载和换资源包场景（单线程窗口），**约定**：运行期不得并发增删池内容；若将来需要支持，应把 `GetSkin` 改为锁内 AddRef 返回 `SAutoRefPtr`（改动面覆盖全部 GETSKIN 调用点，暂不做）。

### 5.4 可接受的无锁读取（按"不崩溃"前提豁免）

- `SSkinButton::_DrawByIndex` 读 `m_colors`（POD），与 `OnColorize`/`SetColors` 的 memcpy 并发 → 颜色撕裂，不崩溃。注意 `SetColors` 当前未加锁，属可接受的不一致；若要收紧，与 `OnColorize` 同样加锁即可。
- `SSkinImgList::SetStates/SetTile/SetVertical` 等初始化期 setter 无锁——必须遵守"发布进池后不再调用"的约定。
- `SSkinAni::m_iFrame` 无锁自增/读取 → 帧号陈旧可接受（对齐 int 硬件原子）。
- SVG 光栅缓存构建（`GetSvgCacheBitmap` 内 `DrawSVG`）与缩放（`Scale()` 内滤波）在锁内执行，毫秒级——首次访问某 (skin, scale/尺寸) 时会串行化其他 UI 线程的 skin/font 查找，冷路径一次性行为，热路径为纯 map 查找。

### 5.5 资源加载瓶颈（非正确性问题）

`SResProviderMgr::LoadImage` 在 `m_cs` 内完成磁盘 IO + 解码，多 UI 线程下图片加载全局串行。正确性安全；如需优化可改为"锁内查缓存、锁外解码、锁内回填"的双检查模型，属后续演进项。

## 6. 结论与建议

### 6.1 结论

在"同一线程树亲和 + 共享对象框架内同步"的两层模型下，SOUI 当前 dev 分支的多 UI 线程安全性**已达到设计目标**：skin 对象、skin 池、资源、渲染后端、通知中心、宿主映射等全部共享点均有明确的同步方案或已固化的约定；无已知可导致崩溃的竞态。剩余风险全部集中在 §5 列出的**约定级条目**上。

### 6.2 建议行动

| 优先级 | 事项 |
|---|---|
| P1 | 在《多线程编程指南》类用户文档中固化 §1.2 三条跨线程通道与 §5.2 SStringT 禁令 |
| P1 | 在 `SObjectFactoryMgr`/`SNamedID` 头文件注释中写明"启动期单线程注册"硬约束 |
| P2 | `SSkinButton::SetColors` 补锁（与 `OnColorize` 对齐） |
| P2 | 若将来支持运行期换皮肤包与并发 RemoveSkin，`GetSkin` 改锁内 AddRef 返回 `SAutoRefPtr<ISkinObj>` |
| P3 | `SResProviderMgr::LoadImage` 双检查模型，缓解解码串行瓶颈 |
| P3 | 真实多 UI 线程压测（双线程同绘/同染/同 Scale 一个 skin，ASan/TSan 或 stress 运行）——目前仅门禁静态覆盖 |
