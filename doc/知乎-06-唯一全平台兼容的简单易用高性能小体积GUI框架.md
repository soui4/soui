# 全平台、简单、快、小：为什么我说 SOUI 是唯一四项全占的 C++ GUI 框架

*（仓库目录 `soui4`，内核版本 5.3.2.5，官网对外标 SOUI5，本文统称 SOUI。标题里的"唯一"有明确限定条件，见第〇节；文末也列出边界。数据取自 2026-11-17 源码实测与当前 HEAD，WASM 移动端结论按 2026-11-20 更新。）*

---

## 〇、先把"唯一"说清楚

GUI 选型有个几乎无解的老问题：**四个好东西，你通常只能挑两个。**

- 要跨平台，就得接受一套新语言、新模型、新工具链（Flutter 的 Dart + Widget、Qt 的 MOC + 信号槽、Electron 的 JS + Chromium）；
- 要学习成本低，就往往被绑在一个平台上（Win32/MFC、Cocoa、GTK）；
- 要性能好、体积又小，就得放弃完整控件体系和声明式布局（Dear ImGui 是典型）；
- 要有完整控件和可视化设计器，通常就把 VM 或几百兆运行时一起拖进来。

我写这篇的目的，是论证 **SOUI 是唯一一个把这四项同时做到的通用 GUI 框架**。但这话必须加限定词，否则就是空话：

> **"唯一"指的是**：在提供**完整通用控件体系 + XML 声明式布局 + 原生渲染**的 GUI 框架这个集合里，同时满足——
> ① 覆盖桌面、移动、鸿蒙，且同一套抽象能下沉裸机、上移浏览器；
> ② 不用换语言、不用换编程模型；
> ③ 编译到原生机器码、无 VM，有可核对的帧率/帧耗时数据；
> ④ 核心 2.3 MB 起，应用通常在 3~10 MB 量级。

按这四把尺子量一遍，格局是这样的：

| 框架 | ① 全平台 | ② 简单易用 | ③ 高性能 | ④ 小体积 | 缺什么 |
|---|---|---|---|---|---|
| **SOUI** | **8 目标**：Win/Linux/macOS/iOS/Android/OHOS/FreeRTOS/WASM | C++ + Win32 模型 + XML，零新语言 | 原生机器码、无 VM；帧率随平台/负载而异（WASM 游戏页 57 fps，裸机数值见第三节） | 核心 2.3 MB，应用 3~5 MB | 见第六节边界 |
| Qt 6 | 桌面 + 移动（无 OHOS、无裸机） | 自有 Q\* 体系，需学 signals/slots、元对象 | 原生，但移动端双 UI 线程 | 数十 MB | ②④，以及①的极端端 |
| Flutter | 桌面 + 移动 + Web（非裸机） | 换 Dart + 声明式 Widget 树 | 有 VM，自绘 | ~10 至数十 MB | ②④ |
| Electron | 桌面（移动靠 Capacitor） | 会 Web 即可 | Chromium + Node，内存数百 MB | 100 MB+ | ③④ |
| wxWidgets | 桌面为主，无移动/裸机/Web | C++，但用原生控件 + 跨 API 适配 | 原生 | 小 | ①（借系统控件，无自绘体系） |
| Dear ImGui | 渲染后端多，但不是应用框架 | C++ 易上手 | 极快 | 极小 | ②④（无完整控件体系、无 XML 布局/设计器） |

**没有第二家同时落在四列里。** Qt 和 Flutter 在①上很强，但②和④失守；Electron 在②上最省事，③④完全不是一回事；wxWidgets 和 ImGui 在③④上漂亮，但要么平台不全，要么根本不是一套完整应用框架。

这就是本文的全部论点。下面四节分别拆开讲这四件事是怎么做到的——重点不是"我们也有"，而是**为什么只有这一家能同时有**。

## 一、全平台：不是"多写几套适配层"，是一个 Win32 形态的 API 贯穿 8 个目标

### 1.1 先把平台清单摆出来

| 目标 | 窗口/启动方式 | 2D 渲染 | 状态 |
|---|---|---|---|
| Windows | 原生 Win32 | GDI / Direct2D / Skia | 产品级（参考实现） |
| Linux | X11 + 自实现 messenger | Cairo / Skia | 产品级 |
| macOS | Cocoa | CGContext / Skia | 产品级 |
| iOS | UIKit，实现 `UITextInput` | CGContext / Skia | 产品级 |
| Android | `SouiView` 继承原生 View | Skia | 产品级 |
| OpenHarmony | ArkTS/JVM 侧启动 + `PlatformAPI` | Skia | 产品级 |
| **WebAssembly** | 浏览器沙箱 + 宿主 JS | **canvas2d / cairo 双后端** | **产品级（浏览器）** |
| **FreeRTOS** | 无 OS，消息泵跑在任务里 | cairo → 内存帧缓冲 | 能力证明级 |

七个是产品级（含浏览器），FreeRTOS 是"能跑、有真机性能参数、但有明确缺口"的能力证明级——分档理由见第六节。**把八个都说成"生产就绪"是不实的**，我的"唯一"主张建立在真实的那一档上。

### 1.2 `swinx`：Windows 上不编译的 Win32 兼容层

跨平台的难点从来不是"能不能画出来"，而是**你写的代码到底是哪一套 API**。SOUI 的选择很反直觉：它不发明新 API，而是在非 Windows 平台上把 Win32 GUI 的那一套重新实现一遍。

- **57 个公共头**，绝大多数与 Windows SDK 同名同结构（`windows.h` / `winuser.h` / `wingdi.h` …）；
- **209,615 行实现 / 303 文件**，落在 `swinx/src/platform/<平台>/` 下；
- **Windows 上整个兼容层不参与编译**，直接用系统 SDK——所以 Windows 不是"又一个移植目标"，而是参考实现；
- 各平台用自己的消息循环和启动器；Android / OHOS 没有独立启动器，由 JVM / ArkTS 拉起，平台桥（剪贴板 / 窗口 / IME / 音频 / 路径）填进 `PlatformAPI` 结构体后由 `PlatformAPI_Init` 注册。

这意味着**你在 Windows 上积累的 Win32 经验、代码、调试直觉，全部可以搬到另外七个目标上**。API 形态始终一致：`CreateWindow` / `GetMessage` / `INVALIDATE` / HDC / COLORREF……只是实现者从 OS 换成了 `swinx`。

一个很硬的旁证：两个真实应用（中国象棋、基金持仓）的业务源码里，`__ANDROID__` 出现 **0 次**。没有 `#ifdef` 地狱，也没有"平台适配目录"里堆一摞只在某端生效的补丁。

### 1.3 能伸到最远的两端，才证明抽象选对了

判断一个跨平台框架是不是"真抽象"，看它能不能到最不像 GUI 的地方还能用。SOUI 的两个极端都有实证：

- **没有 OS 的 MCU**：ESP32-S3 真机，320×240 SPI 屏 + 电容触摸，跑完整 `SApp` + XML 布局 + 动画，固件 **3.91 MB**（6 MB app 分区余 35%），单动画稳态 **56~58 fps**（frame 17.3 ms / paint 14.2 ms），双动画约 **40 fps**。上游只改 **4 处**，内核零移植改动。
- **没有原生窗口的浏览器沙箱**：三个真实应用（控件画廊、中国象棋、基金持仓共用同一份 `soui-host.js`），canvas2d 与 cairo 双后端，可选真线程（`SOUI_WASM_PTHREADS`）。桌面与移动浏览器均已人工验证触摸（触摸屏 / 触控板）、软键盘、中文输入法，**达到生产可用**。

两者复用的是**同一个"无原生窗口服务器、软件渲染到内存帧缓冲、宿主负责呈现"的蓝图**：四个宿主接缝——帧缓冲、上屏、输入注入、消息泵——同构。第三个宿主形态要接进来，改动量被压到"一个 `swinx` 平台后端 + 一个宿主壳"。

**为什么这事只有 SOUI 做得到？** 因为它的抽象层选在"Win32 GUI API"这个足够薄、又足够完整的位置上。Qt 的抽象是自建的 `Q*` 体系，挪到裸机要重写；Flutter 的抽象绑定在 Dart VM 和 Skia 上，挪到裸机等于换框架；Electron 的抽象就是 Chromium 本身。而 Win32 API 只是一组**契约**——在哪实现、用什么实现，从来不是契约的一部分。

## 二、简单易用：不发明新模型，把你已有的技能直接折算过来

"简单"不是文档写得漂亮，而是**你要学的新东西有多少**。SOUI 的答案是接近零：如果你会 C++ 和 Win32，你已经会大半了。

### 2.1 你写的东西长这样

UI 在 XML 里声明——下面这段改编自 `demos/demo/uires/xml/` 里的真实窗口布局（属性语法、skin 名、控件类都是现成的）：

```xml
<SOUI trCtx="dlg_main" title="SOUI-DEMO" width="1000" height="700"
      bigIcon="ICON_LOGO:32" smallIcon="ICON_LOGO:16" resizable="1">
  <root class="cls_dlg_frame" cache="1">
    <caption pos="0,0,-0,30" show="1">
      <text font="face:微软雅黑,size:13,bold:1" colorText="#385e8b">标题</text>
      <imgbtn id="IDCANCEL" skin="skin_chrome_tab_close" pos="-30,5" size="20,20" tip="close" />
    </caption>
    <button class="cls_btn_primary" name="btn_ok" pos="0,40,100,30">确定</button>
  </root>
</SOUI>
```

C++ 侧只管逻辑，用 WTL 风格的消息映射表 + 事件订阅：

```cpp
SOUI_MSG_MAP_BEGIN()
    MSG_WM_CREATE(OnCreate)
    MSG_WM_DESTROY(OnDestroy)
    EVENT_NAME_COMMAND(L"btn_ok", OnOK)
SOUI_MSG_MAP_END()

void OnOK() { /* 业务代码，八个目标共用 */ }
```

关注点分离是**框架强制的**，不是靠团队纪律：XML 节点名经 `SObjectFactory` 映射到 C++ 类，属性经 `SObjectImpl::InitFromXml` 走 `SetAttribute`；`<include>`、模板、命名空间、`style`/`class` 复用都在 XML 侧解决。

### 2.2 真正降低日常成本的几处设计

| 能力 | 是什么 | 省掉的是什么 |
|---|---|---|
| **消息映射 + sigslot 双模式** | 同一份事件定义既能写进映射表，也能 `SubscribeEvent` 订阅 | 不必在"集中式代码"和"灵活订阅"之间二选一 |
| **类 COM 架构** | 接口抽象 + 引用计数，`SAutoRefPtr<T>` 做 RAII | 跨模块边界不必手工管生命周期，也没有 GC 停顿 |
| **可视化设计器** | `demos/uieditor`，构建 demo 即得 | 不必在代码里手调坐标 |
| **资源热重载** | 由编译参数 `SOUI_ENABLE_RELOAD` 决定（库级开关，默认 OFF，非 debug 专属），打开后运行期按 F5 整窗重载 XML/皮肤，向 SHostWnd 的新 root 抛 `EVT_RELOAD`（非广播） | 改一个颜色不用重启应用；旧订阅失效要重挂，这是代价 |
| **skin 热换** | 中国象棋走 WebSocket 分块下载 → MD5 校验 → 解压 `theme_cache/`，服务端按平台下发 | 主题作为数据运营，不必发版 |
| **内置 Lua 5.4** | `ScriptModule-LUA`，XML + Lua + JS 组合扩展 | 逻辑热更不必重编 C++ |
| **单时间轴动画** | `ITimelineHandler` + `IValueAnimator` 共用 10 ms 脉冲；无动画时宿主零定时器 | 不必为每个动画起一个 timer |
| **布局即属性** | `width`/`height`/`posX`/`weight` 等布局输入本身就是可动画的属性 | 动画不需要另一套属性模型 |

其中最后两条值得单独说。很多框架的动画和布局是两个孤岛，做"按钮点击后变宽、兄弟控件让位"要手写一堆同步代码。SOUI 里 `ofLayoutSize` / `ofPosition` 直接把动画写在布局输入上，每帧写值后立刻重排——`GetWindowRect()` 拿到的就是新值，兄弟窗口会跟着让位。框架自己也在用这套：切页（`SStackView`）、页签滑块（`STabCtrl`）、焦点框（`SRootWindow`）都建在它之上。

### 2.3 和多目标一致性合起来看

换目标只是换工具链：裸机用 `soui_fr_project(...)`（有无 `SIM_HOST` 之别）、WASM 用 `-DSOUI_BUILD_WASM_DEMO=ON`、Android/OHOS 走各自的 CMake 配置——**不需要为每个目标维护一套工程文件和一套业务代码**。

对老项目还有一份 30 KB 的迁移指南（`doc/SOUI2-3升级到SOUI4-迁移指南.md`），在三套源码上逐条核对 3.0→4.0 的破坏性变更，每条都带 `文件:行号` 出处。"能不能搬过来"这件事有书面答案，而不是一句"应该可以"。

## 三、高性能：不是跑分好看，是每一帧的账都对得上

> **先划清口径**：下文 56~58 fps 是 **ESP32-S3 裸机 + 320×240 软件渲染**这一极端约束下的实测值，**不是 SOUI 的性能上限**——桌面原生 GDI/D2D 与移动端 Skia 的上限远高于它，那个场景里真正限制帧率的是显示器刷新率和应用逻辑，不是框架。裸机数字的意义在于"同一套框架在几乎没有资源的 MCU 上还能跑到多少"。

### 3.1 大数据量：10 万条列表仍是 60 fps

`SListView` / `SMCListView` / `STreeView` / `STileView` / `SComboView` 走 MVC 虚表：内存占用只取决于可视区实际可见的 item（通常 5~10 个 view），**与数据总量无关**；公开的性能口径是 10 万条数据滚动保持 60 fps。这是 DirectUI 相对"一个数据一个原生 View"最直接的胜利——没有 10 万个对象的创建、布局和 GC 压力。

### 3.2 从"标脏合并"到一次真正的修复

性能不是靠堆优化技巧，是靠设计上避免重复劳动。SOUI 的布局是**标脏 + 一次重排**：`RequestRelayout` 只置 `dirty_self` / `dirty_child` 两档并按 `IsWrapContent` 向上传播，真正的 `UpdateChildrenPosition` 由宿主在每次绘制前调一次 `GetRoot()->UpdateLayout()`。所以"一次改 20 个子控件的宽度"只产生**一次**布局 pass。

这套设计真出过一次问题，也能说明它的价值：`SWindow::UpdateLayout()` 原先只把 `dirty_child` 清回 clean，`dirty_self` 不清——root 一旦被置成 `dirty_self` 就再也没干净过，**每帧白跑一次全量布局**。修复后探针 `ld=` 从"每帧脏"变成 `1/1219`（1219 帧里只有首帧脏），**layout 耗时从 550 µs 降到 5 µs**。

注意：这是被测出来的，不是猜出来的。框架带一个零成本绘制探针，同时记录脏区并集、进入/通过/实际绘制的窗口数、阶段耗时——它能回答"没有整窗重绘""没有多画窗口"这类**否定性结论**，而不只是给你一个好看的平均帧时。

### 3.3 两端实跑数据

**ESP32-S3（无 OS，Cortex 级别 MCU）**

| 指标 | 实测 |
|---|---|
| 固件 | 4,098,192 B（≈3.91 MB，6 MB 分区余 35%） |
| 冷启动 → 首帧 | ≈4.4 s |
| 单动画稳态 | **56~58 fps**（frame 17.3 ms / paint 14.2 ms） |
| 双动画（当前设备版本） | 约 40 fps（layered 离屏合成是结构性成本） |
| 资源 | COFF 87 KB / 59 条，与桌面走同一条 `FindResource` 路径 |
| 渲染链路 | `render-gdi` → `gdi/cairo` → PSRAM 帧缓冲 → RGB565 → SPI |

**WebAssembly（浏览器）**

| 指标 | 实测 |
|---|---|
| 整窗重绘 | **1,773 ops / 11.8 ms**，其中帧内 JS 5.3 ms |
| Lua 游戏页（坦克大战） | **57 fps**，idle `rafP95` 16.8 ms |
| 相对同机基线 | ops −9%、span −14%、fps ×2.6 |
| 烟测矩阵 | 35 断言 × 2 后端 |

这组 WASM 数字来自一轮具体的性能优化：三条根因分别是 embind 热路径、measureText 未记忆化、上屏逐像素换序与多次 `putImageData`；改完才是上面的结果。顺带一提，帧数不是靠漏画换来的——探针把"实际绘制窗口数"也记在账上。

### 3.4 性能取向的本质

SOUI 的性能优势不是某个渲染器写得特别快，而是**没有中间层**：

- 原生 C++ 编译到机器码，没有 Dart VM、没有 V8、没有 Chromium；
- Windows 上直接用系统 GDI/D2D，swinx 根本不参与编译；
- 消息泵、布局、绘制是同一条路径在各端复用，不存在"桌面快、移动另算"；
- 动画共用一条时间轴，多个并发动画不会相位漂移；没有动画时宿主一个定时器都不起。

对一个 GUI 框架来说，"少做无用功"比"把有用功做得更快"收益大得多。

## 四、小体积：从 2.3 MB 核心到 3.91 MB 固件

### 4.1 各端实测体积

| 场景 | 体积 |
|---|---|
| 核心最小编译（Release x86，动态库，仅必需模块） | **约 2.3 MB** |
| 常规配置 | Windows ~4 MB / Linux ~10 MB / macOS ~7 MB |
| Windows 单文件绿色版（RC 嵌入资源） | 一个 `.exe` 直接跑，3~5 MB |
| ESP32-S3 固件（含 cairo + 59 条资源） | **3.91 MB** |
| WASM canvas2d 演示（含 Lua + Scintilla 可选功能） | **全套 5.5 MB** |
| WASM cairo 演示（含内嵌字体） | 6.18 MB + 19.6 MB = **26 MB** |
| 中国象棋 wasm 上线档（不含可选模块） | `.wasm` **3.47 MB** + `.data` **0.5 MB** |
| 基金持仓 wasm（启用 editlite） | `.wasm` **3.09 MB** + `.data` 45 KB |

对照一下：Qt 数十 MB、Flutter 10 至数十 MB、Electron 100 MB+。**同一个应用用 SOUI 和用 Electron，差的是两个数量级。**

### 4.2 体积是怎么压下来的

**第一，渲染后端是插件，不是捆绑包。**

| 后端 | 体积 | 用在 |
|---|---|---|
| GDI / Direct2D | ~200 KB | Windows |
| Skia | 3~4 MB | 移动 / Apple（统一渲染效果） |
| Cairo（swinx 内置） | 3~4 MB | Linux / 裸机 GDI 兼容 |
| canvas2d | 复用浏览器字体，不入字体 | 浏览器默认 |
| WGL 兼容面 | 复用系统 OpenGL | 硬件加速，不改上层代码 |

Windows 上用 GDI 渲染，渲染模块 200 KB 左右，整个应用控制在 3~5 MB；不需要的后端一字节都不 link 进来。

**第二，可选功能按需编译，不进默认包。** 5.5 MB 的 wasm 演示是**功能最全的档位**——把 Lua 脚本引擎和 Scintilla 代码编辑器两个可选模块都编了进去；两个真实应用都不带这两个模块。`SOUI_EDIT_LITE=ON` 再用自实现的轻量 `SEdit` 取代 RichEdit 后端（同时把 `SOUI_BUILD_RICHEDIT` 强制 OFF），基金持仓 wasm 实测 **3,093,990 B（3.09 MB）**，比演示档小 2.4 MB。

**第三，字体策略明码标价。** WASM canvas2d 用浏览器字体，省掉 20 MB；cairo 分支保留内嵌字体换取**字形可控**——同一套 UI 在不同系统上字形一致。这不是"被淘汰的旧方案"，而是一次显式交换：要确定性，就付出 19.6 MB 的 `.data`。同机实测 canvas2d 5.5 MB vs cairo 26 MB，差 4.7 倍。

**第四，资源编译进二进制，不靠外挂目录。** 一份 Windows `.rc` 在三端同源编进 PE/ELF/Mach-O（`SetSysResPeHandle` / `SetAppResPeHandle`）；FreeRTOS 侧换成 `uires.idx` → uiresbuilder → windres COFF → `.incbin`（`.balign 8`，Cortex-M 非对齐会 fault）。端到端同一条 `FindResource` 路径，既没有运行时解压目录，也没有散落的资源文件。

**第五，交叉编译时按目标裁剪。** 裸机用 `--gc-sections` 压进 4 MB FLASH（已做成 CI 断言）；WASM 用 `-Os` + 静态链接 + canvas2d 去掉整族 C 库。

> 需要克制的一点："最小"要限定在"提供原生渲染 + 完整控件 + XML 布局的全功能 GUI 框架"这个范畴。2.3 MB 是严格条件下的最优值，实际取决于配置。但在**同等功能集的框架**里比，它确实是最小的那一档。

## 五、四件事为什么能同时成立：它们其实互为因果

看到这里你会发现，"全平台"和"小体积"通常是矛盾的——跨平台层越厚，体积越大。"简单易用"和"高性能"也是——抽象越高级，越容易藏住成本。SOUI 能四项全占，根因在五个架构选择：

**1. 抽象层选对位置。** Win32 GUI API 是一组**契约**，不是一套实现。Windows 上由 OS 实现，其它地方由 `swinx` 实现。这既是"简单"（你会 Win32 就会）的来源，也是"全平台"（换个实现者就能换宿主）的来源，还是"小"（只实现 GUI 必需的 API 子集，不像 Wine 拖进完整 Windows 运行时）的来源。

**2. 没有 VM、没有中间层。** SOUI 全部编译为各平台原生机器码，直接调原生图形 API，没有字节码解释、没有 JIT、没有 DOM 树到原生控件的映射。体积和性能在这里是同一个原因的两个结果。

**3. 宿主接缝极窄。** 只有四个：帧缓冲、上屏、输入注入、消息泵。接口窄 ⇒ 新宿主的适配成本低 ⇒ 能伸到 MCU 和浏览器这种"最不像 GUI"的地方 ⇒ 反过来证明抽象是真的，不是为几端特制的拼接。

**4. 资源和主题是运行期字符串键 + 提供器链。** `IResProvider` 可以是 PE、文件、内存块，也可以是你自己实现的任何对象（配置面 `ResType_Mem` / `SetAppResMem`）；链尾部覆盖实现主题换肤。这让"一套 UI 多处复用、皮肤可数据化运营"不需要复制代码。

**5. 统一时间轴 + 标脏合并。** 动画只写状态、刷新由一次脉冲统一发起；布局只标脏、绘制前合并重排。代码更少、状态更可控，性能自然更好——这里的"简单"和"高性能"是同一件事的两面。

一句话：**它薄，所以能跑到处；它薄，所以快且小；它用的是你早就熟的 API，所以学起来也薄。**

## 六、诚实的边界：四项全占，不等于没有边界

我不打算把"唯一"写成"完美"。以下缺口同样可逐条核对：

1. **FreeRTOS 是能力证明级，不是通用发布质量。** 字形只烘了 ASCII 0x20-0x7E（中文要按码位重烘）、`<edit>` 无输入法、只有一块板一块屏、双动画 40 fps 低于单动画 56 fps。
2. **移动三端只有编译门禁。** Android / OHOS / iOS 都进了 PR 门禁（交叉编译 + iOS 静态库 Mach-O 复核），但**三端都不跑**——没有运行期回归，宿主库和 `PlatformAPI` 桥接只能靠人工验。
3. **WASM 的自动化在 node 侧。** 移动端浏览器的触摸、软键盘、中文输入法是人工验证通过的（生产可用），但还没进 CI；多窗口合成只有 swinx 层像素自测（13 项），没有应用层烟测驱动下拉/菜单/tooltip。
4. **自绘 UI 不复用系统原生控件。** 原生控件插槽目前只有 3 个；系统级 OLE 拖放也没有。你要的是"和原生控件长得一模一样"还是"各端长得一模一样"，这里要选清楚。
5. **许可：** 自有商业条款，非商用免费。商用前请按官网条款确认，别把"开源"当成默认前提。
6. **栈与字体有具体约束。** WASM 需要 32 MB 栈（建窗递归按桌面线程栈深写）；要可控字形就得走 cairo 分支，代价是 19.6 MB 的 `.data`。

这些是**工作量和流程问题**，没有一项需要推翻前面的架构判断。把它们摊开，是为了让你在选型会上问对问题，而不是等我被问住。

## 七、谁该选它，以及怎么在两天内自己验完

### 适合

- 有 Windows / Win32 / WTL 背景，想低成本扩到全平台（含 OHOS）的团队；
- 同时要桌面和移动端，且希望同一套代码还能下到嵌入式、上到浏览器；
- 在意体积与启动速度的工具类、游戏类、嵌入式 GUI；
- 需要单文件绿色部署、或需要运行期换肤/热更的桌面应用；
- 想用 C++ 一把梭，不想引入 Dart、QML、GObject 等第二套技术栈。

### 不太适合

- 团队只有 Web 前端经验，且产品本质是 Web 内容分发（选 Electron/Tauri）；
- 强依赖系统原生控件外观与无障碍语义的场景（自绘 UI 的边界在此）；
- 强依赖 Qt 生态库的既有项目（迁移成本大于框架本身收益）。

### 两天怎么验

**第 1 天，零构建。** 用浏览器打开三个 wasm 在线演示——控件画廊（十二页控件，最全）、中国象棋（联网对战客户端）、基金持仓助手（真实在线取数）。切页、拖动、在 Lua 游戏页按方向键、在编辑框里打几个汉字；**再用手机打开同一个页面**，轻点、上下滑、点编辑框调软键盘、用中文输入法打字。这条路径已人工验证通过，是"生产可用"最直接的复核。

**第 2 天，跑源码。** 从 Actions 下载 Windows 静态编译的 `demo.exe` 看完整控件表现，再编一遍 `demos/demo` 和 `demos/uieditor`；想看"全平台"成色，对照中国象棋在桌面 / Android / wasm 下的源码目录——业务代码是同一份。跑 `ctest` 看门禁：当前 **633 条 headless 用例全过**（门禁总数 638，另 5 条 GUI 烟测需显示环境）。

如果两天后你发现最在意的是"和原生控件像素级一致"，那 SOUI 不是答案；如果最在意的是"一套代码跑到哪都对得上、还小还快"，那大概率没有第二个选项。

## 结语

跨平台框架这些年给的选项，大多是"用某种便利性换另一种便利性"。SOUI 的不同之处在于它**没有要求你放弃任何东西**：你继续写 C++ 和 Win32 风格的代码，它负责让这份代码在八个目标上都成立；你得到完整控件和设计器，但核心只有 2.3 MB；它快，但不是靠砍功能换来的快。

"唯一"这个词很重，所以我把它限定在一个具体集合里，也把边界逐条写了出来。但在这四条同时成立的意义上——**全平台兼容、简单易用、高性能、小体积**——我确实找不到第二家。
