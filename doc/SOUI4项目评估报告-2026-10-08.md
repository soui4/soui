## 〇、结论与速览

> 本章不展开论证，只给出全文结论、核心数据与章节导航；逐条论证见后文对应章节。

### 0.1 一句话结论

SOUI4 是一套**以 Win32 API 语义为统一编程面**的 C++ DirectUI 框架，借助自研的 `swinx` 兼容层，让**同一套 C++ UI 与业务代码**在 Windows / Linux / macOS / iOS / Android / OpenHarmony 六端原生运行；其类 COM 引用计数（`AddRef/Release` + `SAutoRefPtr`）系统性地降低了 C++ 内存泄漏风险；以 `games/cnchess` 为例，核心绘制/逻辑代码零平台宏、`__ANDROID__` 在**业务源码**中出现次数为 **0**，证明"一次编写、六端运行"是**工程现实而非口号**。同时，内置的 `ScriptModule-LUA` 组件把"XML 声明 UI + Lua 写玩法逻辑"的免编译迭代路径打通——XML 事件属性直挂 Lua 全局函数、整套 SOUI API 经 `exports/` 绑定面暴露给脚本，`demos/demo` 中的两个完整小游戏（跑马机、8×8 消消乐，合计一千余行 Lua）即是可运行的实证。控件完整性上，六个列表控件（`SListCtrl`/`STreeCtrl`/`STreeView` 与 `SViewBase` 系 MVC 虚拟列表）已具备统一的多选、橡皮筋框选与键盘导航框架，以 37 条无头门禁用例覆盖全部交互语义（§4.2）。脚本侧同样达到可验证的完整度：`ScriptModule-LUA` 导出面已补齐到与 soui4js（QuickJS 版）对等的程度（43 个导出文件、约 1,470 处注册），并配 **27 条无头生命周期用例**；`demos/demo` 的消消乐即该能力的端到端实证——交换 / 消除 / 下沉动画组、飞金币抛物线入账链、七段 LED 滚动计分与洗牌绕行动画**全部由 Lua 脚本编排**，改脚本免重编译（§5）。

### 1.6 模块划分

- **`SOUI/`**：DirectUI 内核——窗口树（`SWindow`）、消息路由（`SwndMsgCracker.h`）、事件系统、布局、动画、XML 对象工厂（`SObjectFactory`）；其 `control/` 子目录收纳**基础控件**（当前 39 个控件头文件，含 1 个聚合头 `SouiCtrls.h`），MVC 虚拟列表 `SListView`/`SMCListView`/`STreeView`/`STileView`/`SComboView` 即位于此处，停靠体系另有 `SDockBar` 与其浮动窗口 `SDockFloatWnd`。
- **`utilities/`**：与 UI 无关的基础件——接口定义（`interface/`）、引用计数实现（`helper/obj-ref-impl.hpp`）、XML（`xml/SXml.h`，pugixml 封装）、字符串/数学、COM 动态加载（`com-loader.hpp`）。
- **`swinx/`**：跨平台兼容层（详见第二章）。Windows 下**不编译**；作为 git 子模块独立演进。
- **`components/`**：16 个可独立链接的组件——`render-skia`/`render-gdi`/`render-d2d`（渲染）、`imgdecoder-stb`/`imgdecoder-wic`/`imgdecoder-gdip`（解码）、`resprovider-zip`/`resprovider-7zip`（资源）、`ws`/`network`/`httpclient`/`TaskLoop`/`SIpcObject`（网络与任务）、`ScriptModule-LUA`（脚本，见第五章）、`log4z`、`translator`。**按需装载，未用组件不链入**——这是体积可控的关键。
- **`controls.extend/`**：扩展控件——基础控件之外的**可选额外控件**集合（属性网格 `SPropertyGrid`、日历 `SCalendar2`、图表 `hellocharts`、网格 `gridctrl`、Scintilla 编辑器、GIF 播放等）。MVC 虚拟列表**不在**此目录，而属于 `SOUI/` 基础控件。
- **`soui-android-lib/` / `soui-ohos-lib/`**：移动端宿主库——把 `SApplication` 托管进 `GameActivity`（JNI）/ `EntryAbility`（N-API），并填写 `PlatformAPI` 结构体；`soui-ohos-lib` 已以 **HAR 包形态**提供（ArkTS 侧经 `Index.ets` 导出 `@soui/ohos`，消费端以源码依赖接入）。
- **`demos/` / `games/`**：示例与跨平台样板（`cnchess` 为六端验证样本；`demos/demo` 内含脚本化双游戏样例）。

> 以上是模块边界。全文沿三条主线展开：**第二章**看跨平台层 `swinx`（全篇评估重点），**第三、四章**看框架自身的工程与开发能力，**第五、六章**看可编程性与线程协作；**第七章**与主流框架横向对照，**第八章**汇总优势与风险，**第九、十章**给出路线图与结论。

## 二、跨端能力：`swinx` 跨平台兼容层

> **本章是全篇评估重点。** 跨端能力决定 SOUI 的差异化是否成立：先看 swinx 的设计哲学与量化现状（§2.1–§2.4），再看它的**兼容边界**与**互操作代价**（§2.5–§2.6），接着两个重组件移植案例收口（§2.7–§2.8），最后用 cnchess 的真实项目做六端实证（§2.9）。

### 2.1 设计哲学：以 Win32 为“世界语”

swinx 不是"为每个平台写一套抽象接口"，而是**重演 Win32 语义**——`include/` 下 **44 个头文件**（`windows.h`/`gdi.h`/`unknwn.h`/`oleacc.h`/`textserv.h`…）与 Windows SDK **同名同结构**。因此 SOUI 内核直接 `#include <windows.h>`，**零平台 `#ifdef`**。

> 价值：下游（SOUI 内核、业务代码）完全不感知平台差异。这与 Qt（自有 Q* 体系）、Flutter（Dart + 自绘）、wxWidgets（每平台原生控件 + 不同 API）的路径都不同——SOUI 选择"让 Windows 程序员用原生手感写一次，六端编译"。

### 2.2 六平台 × 渲染后端矩阵

各 `*.cmake` 用 `file(GLOB)` 把当前平台源文件自动纳入编译，**新增 `.cpp/.mm` 不需改 cmake**。实际编译归属：

| 目标平台 | 平台适配层 | 渲染后端 | 构建脚本 | 平台专有依赖 |
|---|---|---|---|---|
| Windows | （不编译 swinx，用系统 Win32） | GDI / D2D | MSVC/MinGW | Win32 SDK |
| Linux（桌面） | `platform/linux` | `gdi/cairo` | `linux.cmake` | ALSA（可选）、xcb / xkbcommon / dbus |
| macOS | `platform/cocoa` | `gdi/apple` | `macos.cmake` | Cocoa / CoreGraphics / Carbon / CoreServices |
| iOS | `platform/ios` | `gdi/apple` | `ios.cmake` | UIKit |
| Android | `platform/mobile` | `gdi/cairo` | `mobile.cmake` | Android NDK（JNI） |
| OpenHarmony | `platform/mobile` | `gdi/cairo` | `mobile.cmake` | OHOS NDK（`napi` / `native_window`） |

> **设计要点**：`platform/*`（窗口壳/事件循环/剪贴板/IME/拖放/DPI）与 `gdi/*`（绘制）是**两个正交维度**——当前 `platform/` 有 4 个目录（`cocoa`/`ios`/`linux`/`mobile`，`mobile` 同时服务 Android 与 OHOS），`gdi/` 有 2 个（`cairo`/`apple`）。Linux 与 Android/OHOS 复用 Cairo 渲染而平台层不同；macOS 与 iOS 反之。**新增平台与新增渲染后端互不牵连**。

### 2.3 三大核心机制

1. **同符号、分目录实现、链接期解析**（`src/SwinxUtils.h`）
   跨平台公共助手声明集中于 `src/SwinxUtils.h`（如 `swinx_messageBeep`），各平台目录给出**同名同签名**实现。`GLOB` 只把当前平台源文件编入，于是调用方写同一个函数名、正文中**无平台 `#ifdef`**。返回类型统一用 `int` 而非 `BOOL`，是为规避 ObjC++ 中 `BOOL` 是 `bool`/`signed char` 的差异。

2. **`g_platformAPI` 回调机制**（`swinx/include/platform_api.h`，`PLATFORM_API_VERSION = 3`）
   Android/OHOS 无桌面窗口系统、由宿主 App 提供窗口/输入/剪贴板，故共用 `platform/mobile`。在**窗口系统 / 输入 / 剪贴板 / 提示音这类需要平台真实能力的层面**，**转发 `g_platformAPI`**（如 `MessageBeep → audio.messageBeep`，与 `PlaySound`/`ShowSoftKeyboard` 同路），由宿主应用（`soui-android-lib`/`soui-ohos-lib`）补差异。`PlatformAPI_Init`（`swinx/src/platform_api.cpp`）**严格比对版本**，不一致拒绝注册——这是跨版本演进的契约护栏。

3. **非 MSVC 工具链上的 COM 自研**（`src/SUnkImpl.h`）
   gcc/clang 无 `__uuidof`，swinx 用四件套补齐：`DECLARE_INTERFACE_` 宏集（`basetyps.h`）、`__uuidof/__suidof` 降级为 `X::GetIID()`（`guiddef.h`）、`IUNKNOWN_BEGIN/ADD_IID/END` 宏 + `SUnkImpl<T>`（`m_cRef` + `OnFinalRelease` → `delete this`）、`DEFINE_GUID` 以 `__attribute__((weak))` 弱符号防重定义。`BSTR/VARIANT/SAFEARRAY/IDispatch` 全部自研。**这让 SOUI 的 ACC 代码一字不改跨三桌面平台编译**。

### 2.5 兼容的边界：缺口与未覆盖面

前一节（§2.4）给出的是兼容面的**规模**；本节给出它的**边界**——哪些情况下"高保真兼容"不成立。

- **编译层面**：同一份 `#include <windows.h>` 源码六端编译——**成立**，且业务代码基本无 `#ifdef`（见 §2.9 的六端实证）。
- **运行时语义层面**：Win32 的隐式语义（消息派发锁语义、伪句柄、ANSI/Unicode 双轨、GDI 对象生命周期）被刻意模拟，但仍有 **23 项空实现/语义桩**与 **129 项仅声明**（链接期失败而非静默）。空实现里 **14 项是刻意的单值语义**（如 `GetACP` 恒返回 `CP_UTF8`、`SetStretchBltMode` 无对应概念）、**3 项是边界清楚的实现范围限制**（如 `EnumDisplayDevicesW` 仅提供显示器级、不提供设备级），**只有 6 项属真实功能缺口（其中 1 项已澄清、5 项待排期）**——但**这一口径只衡量"声明与实现"是否成对，并不衡量"接口面是否够用"**，后者见下一条。
- **接口面缺口：面向原生控件 / 窗口菜单栏 / 对话框的 API 面尚未建立**（决定"能否迁移既有 Windows 程序"，量级远大于上一口径）：

  - **内置原生控件只有 3 个**：`Static`、`Button`（`src/cmnctl32/cmnctl32.cpp`，124 行最简实现，实际是 `MessageBox` 的零件）、`ListBox`（`src/cmnctl32/listbox.cpp`，**3,023 行**，Wine 完整移植）。**`Edit` / `ComboBox` / `ScrollBar` 与全部公共控件（`SysListView32` / `SysTreeView32` / `SysTabControl32` / `SysHeader32` / `SysIPAddress32` …）均无实现**；`InitCommonControls(Ex)` 在 `commctrl.h:106`、`:139` **只有声明没有定义**。
  - **窗口自己的菜单栏未提供**：`SetMenu` / `GetMenu` / `DrawMenuBar` 在 swinx 中**连声明都没有**；`CreateWindowEx` 的 `hMenu` 参数被存入 `GWLP_ID`（`src/wnd.cpp:358`），不会挂出菜单栏。与之对照，**弹出菜单机制本身是完整的**（`src/cmnctl32/menu.cpp`，1,992 行）。SOUI 侧菜单由自绘控件 `SMenuBar`/`SMenu` 提供（XML 描述），故自身不受影响。
  - **无任何对话框实例化 API**：`DialogBoxParam` / `DialogBoxIndirectParam` / `CreateDialogIndirectParam` / `EndDialog` **全缺**；`.rc` 的 `RT_DIALOG`(5) / `RT_MENU`(4) 仅为资源类型宏、无对应运行时（资源本身的跨端编译可用，见 §2.8）。`src/cmnctl32/msgbox.cpp`（250 行）提供自绘 `MessageBox`，但**按钮文案硬编码简体中文、图标为内置位图**，与系统实现的外观/本地化不同，且无 `MessageBoxIndirect`。
  - **公共对话框反而是完整的一块**：`GetOpenFileName(A/W)` / `GetSaveFileName(A/W)` / `ChooseColor(A/W)`（`src/cmmmdlg.cpp`）；`ChooseFont` 三个桌面端均有实现（Linux `platform/linux/dlghelper.cpp:1843`、macOS `platform/cocoa/dlghelper.mm:712`，iOS 版明确返回 `FALSE`），另有 swinx 私有扩展 `PickFolder(A/W)`。
  - ⚠️ **失败方式与"仅声明"不同，排查成本更高**：类名宏（`WC_EDITA` 等）在 `commctrl.h` 中有定义，故 `CreateWindowEx(0, "EDIT", …)` **可编译、可链接，但运行时因窗口类未注册而返回 `NULL`**——属**静默失败**。
  - **结论**：swinx 的完备度是"**让用 SOUI 编写的应用跨端**"这一目标下的完备度，**尚未达到"让既有 Win32 程序零成本迁移到多平台"**。两者相差"原生控件库 + 窗口菜单栏 + 资源对话框"三块；该目标在能力上可达（`ListBox` 已证明 Wine 控件可整体搬运、消息/GDI/类注册地基稳固），差距属**工作量而非架构不确定性**。

- **真实 API 缺口（6 项，其中 1 项已澄清）**：

  | API | 当前行为 | 影响面 | 判定 |
  |---|---|---|---|
  | `ScrollWindowEx` | 返回 `0` | 滚动区域位块搬运；当前只能整体重绘 | 待排期 |
  | `SendNotifyMessageA` / `SendNotifyMessageW` | 返回 `FALSE` | 跨线程异步投递；`PostMessage` / `SendMessage` 已完整，多数场景可绕开 | 待排期 |
  | `SetWindowExtEx` | 返回 `FALSE` | 视口（window extent）设置 | 待排期 |
  | `SetMenuItemBitmaps` | 返回 `FALSE` | 菜单项位图 | 待排期 |
  | `IsWindowUnicode` | 恒返回 `FALSE`（源码含说明） | swinx 内部统一以 UTF-8 存储窗口文本，UTF-8 对应 Windows 双轨中的"多字节"路径，与 `GetACP()` 返回 `CP_UTF8` 自洽——**刻意语义而非缺陷** | **已澄清** |

  > 即：**待排期的真实缺口是 5 项 API**（`ScrollWindowEx`、`SendNotifyMessageA`、`SendNotifyMessageW`、`SetWindowExtEx`、`SetMenuItemBitmaps`），另 **1 项已澄清**（`IsWindowUnicode`）——合计 6 项。它们**只影响"为通用 Windows 编写、依赖窗口边框/滚动位块/跨线程投递"的第三方代码**；SOUI 自绘场景不阻塞。

- **"仅声明未定义"的最大空白族群**：comctl32 图像列表（36 项）、comctl32 动态数组 `DPA_*`/`DSA_*`（32 项）、Flat 滚动条 `FlatSB_*`（13 项）、剪贴板格式枚举与查看链（9 项）、窗口子类化 `SetWindowSubclass` 族（4 项）。SOUI 用自己的图像/容器/消息钩子体系替代，故自身不受影响；但**通用控件库移植时会踩到**。
- **无障碍（ACC）当前状态**：`SOUI_ENABLE_ACC` 是一个贯穿全局的构建开关，**默认 OFF**（`CMakeLists.txt:132`）；打开后 Windows 走系统 `oleacc`，macOS 走 `SNsAccessibility`（NSAccessibility 桥）、Linux 走 `SAtSpi`（AT-SPI2 桥），屏幕阅读器可导航对象树并读出文本/数值内容。**OHOS 端在构建层被强制关闭**（`CMakeLists.txt:120`：`if(IS_OHOS) set(SOUI_ENABLE_ACC OFF)`）——其影响与处置见 §8.2 风险 4。

**结论**：在"**承载 SOUI 自身所需**"这一范围内，swinx 做到了**高保真兼容**而非"画布级"近似；其严格等于 Windows SDK 的公共头面 + 链接期解析机制，是项目最值得称道的设计资产。但需明确一处能力边界：**"让任意既有 Win32 程序零成本迁移"目前尚未达成**——所差的是原生控件库、窗口菜单栏与资源对话框三块接口面（本节第三条），差距属工作量而非架构不确定性。

### 2.6 与原生开发的互操作成本（“无缝互通”的另一半）

兼容面之外还有一个常被问到的问题：**调系统能力时，用 SOUI 要不要为框架额外付出代价？** 本节给出结论与横向对比。

**核心卖点**：SOUI 的价值不在于"另造一套与原生对立的 UI 栈"，而在于**用 SOUI 开发的应用可以与原生开发无缝互操作**。以"调用摄像头"这一典型原生能力为例：

- **原生开发**：直接用系统 API 调摄像头（Android `Camera2` / OHOS `@ohos.multimedia.camera` 等），无需任何框架中介。
- **SOUI 开发（调摄像头）**：移动端开发者**自己写一个 JNI（Android）或 NAPI（OHOS）**，就能在 Java/ArkTS 端与 C++ 端之间交互、调起系统摄像头。这本质上和原生开发调摄像头的方式一致——**所有代码都运行在 SOUI 的 UI 线程上，而该线程就是宿主 App 的原生线程：同一线程、无需线程切换、无需把结果跨线程回传、也无需为摄像头再包一层异步封装，属于"原生开发的另一种方式"**。iOS 端更为直接：C++ 可直接调用 Objective-C，连 JNI/NAPI 都不需要。
- **对比其它跨平台框架调原生能力的额外成本**（相对评估，非绝对结论）：
  - **原生开发**：零成本，直接调系统 API。
  - **SOUI**：JNI/NAPI **同一线程同步调用**，无线程切换、无复杂二次包装（iOS 直连 C++）。
  - **Qt**：原生调用需**切换/桥接线程**后再回 UI 线程，存在跨线程模型成本。
  - **Flutter**：若框架未封装该能力，需写 **Platform Channel（MethodChannel）封装 + 序列化**，开发量显著。
  - **Electron**：需经 Node 原生插件 / C++ Addon 与系统 API 对接，包装工作量同样大。
- **机制支撑（厘清 `g_platformAPI` 的职责边界）**：`g_platformAPI` 是 **swinx 窗口系统与移动端 GUI 框架之间的交互桥**（窗体创建、输入、剪贴板等窗口系统层面由宿主 App 补上），**并不是"调系统能力"的通道**；像摄像头这类系统能力，是开发者按原生开发习惯自己写 JNI/NAPI 完成的，与 swinx 的 GUI 桥无关。此外 `SRealWnd`（`SOUI/include/control/SRealWnd.h`）可把真实原生窗口嵌进 DirectUI 树（XML `<realwnd wndclass="edit" .../>`，由 `IRealWndHandler` 创建/管理真实 `HWND`；Windows 上可直接使用系统窗口类，swinx 平台则需由宿主 App 在 handler 内映射到自建窗口类或移动端原生控件——如 Android demo 的 `className="edit"` 走 `NativeEditView`），`SNativeWnd`（`SOUI/include/core/SNativeWnd.h`）封装原生窗口——开发者既能用 SOUI 写一套界面，又能随时**无障碍调用各平台原生能力**（文件对话框、系统服务、第三方 SDK），不被框架"锁死"。

### 2.7 典型案例：移植 richedit41 与 Scintilla，重组件零改源码跨端

> **这是 swinx"以 Win32 为世界语"最硬核的佐证**：连 Windows 上最难移植的富文本编辑（RichEdit，依赖 Text Services / OLE / GDI+ 一整套私有契约）都被搬到了非 Windows 平台。

- **基础控件 `SRichEdit`**（`SOUI/src/control/SRichEdit.cpp`、`SOUI/include/control/SRichEdit.h`）基于 Win32 **Text Services** 架构（`ITextHost`/`ITextServices`，接口定义在 `swinx/include/textserv.h`），支持 RTF、OLE 对象、字符/段落格式、滚动、撤销重做等。
- **Windows 走系统实现**：`SRichEdit.cpp:21` 定义 `USE_MSFTEDIT` 并做条件编译（`:1351`），直接复用系统 `msftedit.dll`（RICHEDIT50W）。
- **非 Windows 走 swinx + richedit41 移植**：swinx 提供 `richedit.h` / `textserv.h` 这一**与 Windows SDK 同名的 Win32 富文本 API 面**，底层引擎是 `third-part/richedit41/`（**499 个受控文件**，Microsoft RichEdit 4.1 源码移植）。于是**同一份 `SRichEdit` 源码**在 Linux / macOS / iOS / Android / OHOS 上编译运行，富文本能力跨端一致。
- **移动端开关**：Android 通过 `SOUI_BUILD_RICHEDIT`（富文本编辑控件，依赖 richedit41，`soui-android-lib/.../soui4_android.cmake`）按需开启。

- **同一思路延伸到语法着色编辑器 Scintilla**：SOUI 的 `CScintillaWnd`（`controls.extend/ScintillaWnd.cpp`）也是基于 Scintilla 的 **Win32 分支**——经 `Scintilla_RegisterClasses(hInst)` 注册窗口类、`CreateWindowEx(..., "Scintilla", ...)` 建窗、`SendMessage(m_hWnd, SCI_*, ...)` 发消息，XML 语法着色（`SetXmlLexer()`）与代码折叠全部走这套 Win32 消息协议。值得注意的是，**Scintilla 官方本身同时提供 Win32 与 GTK（Unix）两套后端**，但 SOUI **只取 Win32 分支**，靠 swinx 在各平台把 `CreateWindowEx`/`SendMessage`/GDI 这套 Win32 桌面子系统整体模拟出来。`SRealWndHandler_Scintilla` 再把它作为真实原生窗口挂进 SOUI 布局。

**意义**：富文本编辑长期是跨平台框架的"硬骨头"——Qt 用自有 QTextDocument、Flutter/Dart 自研、Electron 借浏览器引擎。SOUI 直接用 swinx 把系统级 RichEdit 契约整体搬过来，既保证了与 Windows 行为的高一致，又把难度最大的控件做成了"零改源码跨六端"；Scintilla 的并入进一步证明：**只要组件存在 Windows 实现，swinx 就足以让它跨平台，而不必为每端另写后端**。

### 2.8 典型案例：RC 资源文件跨桌面端编译（单套 .rc 三端编译 + 单文件发布）

> **这是 swinx"以 Win32 为世界语"在"资源"维度的延伸**——桌面端多数跨平台框架（Qt `.qrc`、Flutter `pubspec` assets、Electron asar）都要求每端维护一套独立资源管线；SOUI 在桌面端反其道而行：**一份 Windows `.rc` 资源文件，Windows / Linux / macOS 三端同源编译、同源加载**。而 Android / iOS / OHOS 等移动端继续使用各自的原生资源机制（APK `assets` / Xcassets / HAP `RawFile`），**不纳入此 RC 编译方案**——移动 App 本就以平台原生包体（apk/ipa/hap）分发，原生资源目录是其既定规范。

- **Windows 资源 API 兼容层**（`swinx/src/resapi.cpp`，声明见 `swinx/include/resapi.h`）：在非 Windows 上提供与 Windows **同名同签名**的 `FindResourceW/A` / `LoadResource` / `LockResource` / `SizeofResource` / `EnumResourceNames` / `LoadString` 等，使上层（含 `SResProviderPE`）零改动跨端运行。
- **COFF 资源解析器**（`swinx/src/coffparser.cpp` + `coffparser.h`，类 `WindResResourceParser`）：运行时按 Windows 资源的三级目录（类型→名称→语言）递归解析 `.rsrc`/`.rdata`/`.data` 段，从数据段抽取实际资源字节；靠链接期生成的 `_binary_soui_coff_o_start` / `_binary_soui_coff_o_end`（macOS 为双下划线 `__binary_…`）符号定位数据区。
- **CMake 编译工具链**（`__cmake/windres.cmake`，`windres_compile_rc` / `target_compile_resources`）：桌面非 Windows 端的四步流水线——
  1. **.rc → COFF**：MinGW `windres --target=pe-x86-64 … -O coff`；
  2. **COFF → 本平台目标文件**：Linux 用 `ld -r -b binary` 转 ELF；macOS 经 `.incbin` 嵌入 `__DATA,__data` 再 `as` 成 Mach-O；
  3. **符号重命名**：`nm` 取符号 + `process_symbols.cmake` 生成脚本，`objcopy --redefine-syms` 统一为固定 `soui` 前缀；
  4. **链接进产物**：`target_link_options` 加 `-rdynamic` + `--version-script=export_res_sym.lst` + `--no-gc-sections`，导出资源符号不被 GC 抹除。
- **单文件发布**：开启 `ENABLE_BUILD_RESOURCE` 后，系统/应用资源经 `SetSysResPeHandle`/`SetAppResPeHandle` 直接读入可执行文件内嵌资源段——与 §3.2 的"资源内嵌单文件部署"同一机制。配合 `tools/src/uiresbuilder`（读 `uires.idx` 一键生成 `.rc2`/`resource.h`/`R.js`，**桌面三端共用同一 `uires.idx`**），UI 资源从"手工维护 resource.h + rc2"升级为"一次描述、**桌面三端复用**"。

**意义**：把"用熟悉的 Windows 资源编辑器、写一份 .rc"的开发习惯直接带到 Linux/macOS，既消除了桌面多端资源管线的重复劳动，又天然支持单文件分发。移动端因天然使用平台原生包体资源（apk/ipa/hap），另行走原生资源路径，不在此方案覆盖范围内。

### 2.9 六端实证：`games/cnchess` 单代码库跨端

> 前两节讲的是兼容层如何设计；本节看一个真实项目如何用它——`games/cnchess` 是 SOUI4 的跨平台样板，“单代码库六端”的结论在这里落到逐文件计数上。

#### 2.9.1 共享结构

- **`client/`**：桌面/iOS 共享 C++ 业务（`MainDlg`/`ChessGame`/`ChessBoard`/`ChessPiece`/`CnchessSkin`/`LoginDlg`/`myprofile`）+ 入口 `main.cc`。
- **`client/android/`**：`GameActivity.java` + gradle + JNI 桥；业务 C++ 不在此，由 gradle 经 `SOUI_ROOT_DIR` 引入 `client/`。
- **`client/ohos/`**：`SouiPlatformBridge.ets`/`SouiScreen.ets` + N-API 桥；`cpp/` 用 GLOB 引入 `client/` 共享源码。
- **`algorithm/`**：AI 引擎（PVS + 置换表 + 杀手/历史启发，移植自 MIT 项目），**纯标准 C++，不依赖 windows.h**。
- **`server/`**：同为 C++（WebSocket 联机 + 机器人复用 algorithm 引擎）。

#### 2.9.2 平台宏分布（业务源码实测）

| 宏 | 出现位置（源码计数） | 结论 |
|---|---|---|
| `__ANDROID__` | **业务 C++ 源码 0 次**（仅 `README.md` 文档提及 1 处） | 平台差异被 swinx + 宿主 lib 完全吸收 |
| `__OHOS__` | 业务 C++ 源码 **0 次**（仅 ohos 目录 CMakeLists / readme） | 同上 |
| `_WIN32` | 入口/资源层：`main.cc`(2)、`server.cpp`(5)、`stdafx.h`(6)、`LoginDlg.cpp`(1)、`MainDlg.cpp`(2)、`cnchess.rc`(2) | 平台分流集中在薄入口 |
| `__APPLE__` / `__IOS__` | `main.cc`(6)、`MainDlg.cpp`(1) | 同上 |
| `__MOBILE__` | `ChessGame.cpp`(4)、`MainDlg.cpp`(4)、`MainDlg.h`(1)、`ThemeDownloadManager.cpp`(1) | 仅区分"移动触屏 vs 桌面弹窗"（移动用 `SModalView` 替代对话框） |

**核心绘制/逻辑文件 `ChessBoard.cpp`、`ChessPiece.cpp`、`myprofile.cpp`、`CnchessSkin.cpp`、`algorithm/*` 完全无平台宏。**

#### 2.9.3 单代码库跨端机制

同一份 `MainDlg/ChessGame/ChessBoard/algorithm` 经**三个薄入口**接入不同宿主：
- 桌面/iOS：`swinx` 提供事件泵与窗口系统，归一为 `WinMain`；
- Android：`soui-android-lib`(JNI) 把 `SApplication` 托管进 `GameActivity`；
- OHOS：`soui-ohos-lib`(N-API) 托管进 `EntryAbility`（ArkTS 侧经 HAR 的 `@soui/ohos` 导出接入）。

资源经 `SAppCfg` 的 `Set*Res*(PeFile/AndroidAsset/OhosRawFile/File)` 抽象加载——业务层只看到 `Render_Skia` + `ImgDecoder_Stb` 一套渲染。**平台差异绝大部分落在 swinx / 宿主 lib 与入口四虚函数，业务代码仅以 `__MOBILE__` 一处开关区分移动/桌面交互**。

> **评价**：这是"一套 C++，六端运行"的强证据。相对 Flutter（需 Dart 重写 UI 层）、Qt（需 QWidget/QML 适配）、wxWidgets（API 随平台变），SOUI 在"业务代码零平台宏"这一点上做到了当前跨平台 GUI 框架中罕见的彻底度。

**本章要点**：

1. swinx 用“重演 Win32 语义”而非“自造抽象层”——44 个公共头与 Windows SDK 同名同结构，实现按 `platform/`（4 目录）× `gdi/`（2 目录）两个正交维度分目录、链接期解析；结果是 SOUI 内核零平台 `#ifdef`。
2. 兼容面在“承载 SOUI 自身”范围内高保真，在“迁移既有 Win32 程序”范围内尚未达成：所差的是原生控件库、窗口菜单栏、资源对话框三块接口面（§2.5），属工作量而非架构不确定性。
3. 同一套 Win32 契约还能整块搬运重组件（richedit41 / Scintilla 的 Win32 分支）与桌面资源（一份 `.rc` 三端编译进 PE/ELF/Mach-O）——这是“一次编写、六端运行”最硬的佐证。

## 三、工程能力：内存 · 体积 · 矢量渲染

> 第二章回答的是“跨平台在技术上怎么做到”；本章换一个视角，考察框架自身在**内存模型、程序体积与矢量渲染**三件事上的工程能力——这决定了它能否在资源受限的场景里被人放心使用。

### 3.1 引用计数与内存管理（解决 C++ 内存泄漏的核心手段）

**机制链**

```mermaid
graph LR
    I[IObjRef<br/>AddRef/Release/OnFinalRelease<br/>obj-ref-i.h:18-37] --> T[TObjRefImpl&lt;T&gt;<br/>m_cRef=1, Interlocked 计数<br/>归零→delete this<br/>obj-ref-impl.hpp:13-55]
    T --> S[SObjectImpl&lt;T&gt; / SObject<br/>Sobject.hpp:28,318]
    S --> W[SWindow : TObjRefImpl&lt;SObjectImpl&lt;IWindow&gt;&gt;<br/>SWnd.h:350-352]
    P[SAutoRefPtr&lt;T&gt;<br/>构造/赋值 AddRef<br/>析构/Attach/Detach 精确控制<br/>obj-ref-impl.hpp:73-269] -->|持有| I
```

- **接口层 `IObjRef`**（`utilities/include/interface/obj-ref-i.h`）：仅 `AddRef`/`Release`/`OnFinalRelease` 三纯虚方法——是 COM `IUnknown` 的**引用计数子集**，**无 `QueryInterface`**（类型安全转换由模板 `sobj_cast<T>()` 替代，比 QI 更轻量）。
- **计数实现 `TObjRefImpl<T>`**（`utilities/include/helper/obj-ref-impl.hpp`）：构造 `m_cRef=1`；`AddRef` → `InterlockedIncrement`；`Release` → `InterlockedDecrement`，**归零时 `OnFinalRelease()` → `delete this`**；`TObjRefImpl2<T,T2>` 解决多重继承下的正确析构类型。
- **智能指针 `SAutoRefPtr<T>`**（同文件）：构造/拷贝 `AddRef`，析构/`operator=`/`Release` 自动 `Release`；提供 `CopyTo`/`Attach`(不增引用)/`Detach`(不释放)/`Get`，语义与 COM `IUnknown` 指针管理一致。

**设计权衡（客观评估）**

- **资源对象一律引用计数**：皮肤 `ISkinObj`、字体池、位图、渐变、布局均以 `SAutoRefPtr` 持有（`SWnd.h`、`SSkin.h`、`SFontPool.h`）；事件参数 `SEvtArgs`、事件槽 `StdFunctionSlot` 等也走计数——**订阅即增引用，回调期间对象不会悬空**。
- **控件树采用裸侵入式链表**（`m_pFirstChild/m_pParent/m_pNextSibling…` 均为裸指针），由父窗口以 owner 语义负责析构（`DestroyWindow`），**不走引用计数**——这是 DirectUI 树的标准做法，**刻意避免父子循环引用导致永不释放**。
- **skin 资源子系统的线程安全模型（多 UI 线程场景）**：皮肤池与 `SUiDef` 的 skin/style/font 路径共用**一把递归临界区**（`SUiDef::GetSkinLock()`，`SOUI/include/res.mgr/SUiDef.h`），全局只存在 `SUiDef → skin` 一层锁序；`GetImage/GetSvg` 在锁内完成懒加载并**返回 `SAutoRefPtr<T>`**（引用计数 + 线程安全获取二合一），`GetDrawable(pImg, pSvg)` 一次加锁同时取齐两类资源；Direct2D 渲染工厂已启用 `MULTI_THREADED`。唯一硬约束是 **skin 自身临界区内不得再经 `GETSKIN` 取其它皮肤**（避免经 `SUiDef` 锁形成 ABBA）。

> **评价**：该设计在"自动回收资源对象"与"避免控件树循环引用"之间取了正确平衡，系统性降低了 C++ 最常见的两类泄漏（忘记 Release、循环引用）；skin 子系统的统一锁模型进一步把"多 UI 线程访问共享皮肤资源"的竞态面收敛到单层锁序。但引用计数本身不防**跨线程生命周期误用**与**外部裸指针缓存**——框架降低了风险而非消除风险，开发者仍须遵守"对外暴露 `SAutoRefPtr`、不缓存裸指针"的纪律。

### 3.2 程序体积

| 手段 | 机制 | 出处 |
|---|---|---|
| 核心精简 | 编译核心约 **2 MB**（动态库） | `README.md:37` |
| 组件按需 | 16 个组件均为独立 target，未用组件（skia/wic/zip/7zip/lua/network…）不链入 | `components/*/CMakeLists.txt` |
| 资源内嵌 | `ENABLE_BUILD_RESOURCE` 把系统/应用资源打进 PE/ELF/Mach-O（`SetSysResPeHandle`/`SetAppResPeHandle`），单文件部署 | `games/cnchess/client/main.cc`、`build_deb.sh`；背后即 §2.8 的 RC 跨桌面端编译技术 |
| 静态/动态可选 | `build_deb.sh` 以 bin 下有无 `libsoui4.so` 判定静态或 DLL 模式；静态模式仅一个 exe，DLL 模式依赖一组轻量 `.so` | `games/cnchess/client/build_deb.sh` |
| 矢量资源 | `uires/svg/*.svg` 体积小、可缩放（实现见 §3.3） | `README` 5.2 起全面支持 SVG |

**客观评估"最小体积"主张**：
- ✅ **相对带运行时/虚拟机的方案成立**：Qt（核心 + GUI 动辄数十 MB）、Electron（Chromium + Node，100MB+）、Flutter（Dart VM + Impeller/Skia 自绘，发行包 10–几十 MB）均显著更大；SOUI 是纯原生 C++、无 VM、无 JS 引擎。
- ⚠️ **准确的体积表述**："最小体积"应限定在"**提供原生渲染 + 完整控件 + XML 布局的全功能跨平台 GUI 开发框架**"这一范畴内。即时模式 / 游戏 GUI 库与 SOUI 分属不同类别，不在同一比较维度。
- ⚠️ **实际体积取决于配置**：静态全链接 + 内嵌全部资源 + Skia 静态捆绑时，单体 exe 体积会上升；"2 MB"指动态链接核心，使用时需按目标配置实测。

### 3.3 渲染层对 SVG 的支持（矢量直绘、无损缩放、高分屏原生友好、AI 友好）

SOUI 没有把 SVG 当作"另一种位图格式"来兼容，而是在**渲染层把它当作一等公民的矢量绘制原语**，因此获得了位图方案难以企及的四个收益：

- **矢量直绘而非栅格化贴图**：`IRenderTarget::DrawSVG`（`SOUI/include/interface/SRender-i.h`）是渲染目标的绘制接口之一，且**四个后端全部实现**（`render-skia.cpp`、`render-d2d.cpp`、`render-gdi/win`、`render-gdi/linux`，另 `render-skia` 内含 `nsvgPathToSkPath` / `nsvgPaintToSkPaint` 把矢量路径在**绘制时刻**转为后端原生路径）。整条链路是"矢量 → 原生路径 → GPU/光栅"，在显示分辨率上一次性成形，**而非先栅格化成某个固定尺寸的位图再拉伸**。
- **无损缩放 + 9-Patch 拉伸**：SVG 皮肤经 `SSkinImgList::SetSvg/GetSvg`（`SOUI/src/core/SSkin.cpp`，XML 皮肤类型 `"svg"`）接入；`DrawSVG9Patch`（同文件 `:84`）让 SVG 像 9-Patch 一样按任意尺寸拉伸而**不糊边**。无论窗口放大、还是 DPI 从 100% 切到 200%，矢量路径始终按目标像素密度重新 tessellate，边缘永远锐利。
- **为高分屏（HiDPI）提供完美支持**：因为绘制发生在目标 DPI 的像素网格上，SOUI 的 SVG 在 Retina / 4K / 移动设备高分屏下天然清晰，不需要为不同 DPI 准备多套位图资源（@1x/@2x/@3x）。
- **与 AI 工具链更好适配**：SVG 是**文本化、可程序化生成与修改**的矢量格式，LLM / 设计工具可直接产出或改写其路径数据（`SOUI/include/core/Svg.h` 提供 `CreateSvgFromFile`/`CreateSvgObj`）；相比像素位图，矢量描述更利于 AI 生成、主题换色、参数化图标等场景。

**意义**：把"矢量图形"下沉到渲染原语而非资源加载器，是 SOUI 在高分屏时代保持"一套资源全端清晰"的关键工程选择，也使其视觉资产能更自然与现代 AI 设计 / 生成工作流对接。

**本章要点**：

1. `SAutoRefPtr` + 控件树裸指针的组合，在“自动回收资源对象”与“避免父子循环引用”之间取了正确平衡；skin 子系统把多 UI 线程访问收敛到 `SUiDef::GetSkinLock()` 的单层锁序（§3.1）。
2. 核心约 2 MB、16 个组件按需装载、资源可内嵌单文件；“最小体积”只对带运行时/虚拟机的全功能 GUI 框架成立，且会随链接与资源配置浮动（§3.2）。
3. SVG 是渲染原语而非图片格式，四个后端均实现 `DrawSVG`——一套矢量资源在 HiDPI 下无需 @1x/@2x/@3x 多套位图（§3.3）。

## 四、开发能力：快速开发与控件完整性

> 上一章讲的是内存如何回收、资源如何不膨胀；本章看开发者实际体验——写 UI 有多快、控件够不够用。脚本化的玩法迭代（第五章）是这条线的延伸，本章只谈 C++ 与 XML 层面的开发效率。

### 4.1 快速开发能力

- **XML 驱动 UI**：`pugixml` 封装为 `SXml`（`utilities/include/xml/SXml.h`）；`SObjectImpl::InitFromXml` 遍历属性→`SetAttribute`；`SWindow::CreateChildren` 支持 `<include>`、模板、命名空间。控件经 `SObjectFactory::CreateObject` 由 XML 节点名映射到 C++ 类——**换皮肤/换布局不改 C++ 代码**。
- **脚本化玩法迭代**：XML 事件属性（`on_command`/`on_init` 等）可直接挂 Lua 全局函数，改脚本无需重编译 C++，配合宿主的 `<script>` 资源加载形成"XML 管布局、Lua 管逻辑、C++ 管能力"的三层分工（机制与实证详见 §5）。
- **皮肤热换**：`games/cnchess/client/ThemeDownloadManager.h` 经 WebSocket 分块下载主题 zip → MD5 校验 → 解压到 `theme_cache/`（跨线程下载机制见 §6.2）；服务端 `server/ThemeResourceProvider.cpp` 按 `dwOSId` 分平台下发。
- **MVC 虚拟列表**：SOUI **基础控件**（`SOUI/include/control/` 与 `SOUI/src/control/`）提供 `SListView`/`SMCListView`/`STreeView`/`STileView`/`SComboView`，大数据集只渲染可见项。
- **列表多选 / 橡皮筋框选 / 键盘导航**：`SListCtrl`、`STreeCtrl`、`STreeView` 与 `SViewBase` 系视图控件（`SListView`/`SMCListView`/`STileView` 等）内置统一的多选框架——多选集合以单项事件 `EventItemSelChanged`/`EventTreeItemSelChanged` 反馈、与单选状态双轨互斥可双向迁移；`SPanel` 提供橡皮筋框选（视觉经 `bandSkin` 属性走皮肤、ESC 快照还原、边缘自动滚动）；Shift = 锚点..光标区间选择（可扩可缩），并配套完整键盘导航（方向键 / Home / End / PgUp / PgDn / SPACE）与焦点框绘制（框架分层、完整交互语义与测试覆盖的专项剖析见 §4.2）。
- **富文本跨平台**：`SRichEdit`（`SOUI/include/control/SRichEdit.h`）经 swinx 移植的 richedit41 引擎实现 RTF / 超链接 / OLE 富文本编辑，一套代码六端一致（详见 §2.7）。
- **控件面**：`SOUI/include/control/` 下 **39 个控件头文件**（含 1 个聚合头 `SouiCtrls.h`），覆盖按钮/编辑/列表/树/表格/日历/日期时间/滑块/开关/标签页/停靠/拆分/着色编辑器等；不满足的可经 `controls.extend/` 追加。

> **评价**：XML + 类 COM 对象工厂使 UI 与逻辑解耦彻底，配合可视化设计器 `uieditor`（在 `demos/` 内，构建 demo 即得），开发体验接近 Android 的声明式布局；再叠加 Lua 脚本层后，玩法逻辑的"改完即生效"回路也不需要 C++ 编译器参与。这是 SOUI "快速开发"主张的实质支撑。

### 4.2 控件完整性（含列表族多选/框选专项）

控件是框架交付能力的最终形态。本节先给出控件面的总账，再对列表族控件的多选 / 框选能力做专项剖析——自绘列表控件普遍缺失的一块能力，在本代码基线中已完整落地，并由无头门禁测试成规模覆盖。

**控件面总账（当前实测）**

| 层 | 规模 | 构成 |
|---|---|---|

**列表族多选 / 框选专项（六控件统一框架）**

覆盖范围：`SListCtrl`、`STreeCtrl`（自绘实列表）与 `SListView`/`SMCListView`/`STileView`/`STreeView`（MVC 虚拟列表，共同基类 `SViewBase`）。框架分两层，控件层只负责把 band 矩形映射到各自的数据模型：

- **手势层（`SPanel`，公共基类）**：橡皮筋框选手势与绘制——`StartRubberBandSel`/`EndRubberBandSel` 驱动，band 视觉经 `bandSkin` 属性走皮肤（默认内置 `_skin.sys.selband`，未配置回退 `colorSelBand` 色绘制）；`bandEnable` 属性 / `EnableBandSel()` 把"框选手势"与"多选状态"**解耦**（关 band 后拖动落回惯性滚动，多选点击路径不受影响）；**band 内容锚定**——拖动中滚动列表时 band 以内容坐标锚定，滚出视口的条目照常进选择集；边缘 24px 自动滚动（40ms 定时、按距离分档 1~4 行/tick）；ESC 取消并按选择快照还原（`SnapshotSelItems`/`RestoreSelItems`）。
- **状态层（`SViewBase` + 各控件）**：多选集合与单选高亮**双轨互斥**——多选态的查询只读多选集合，单选协议事件不触发，模式切换即纯记录迁移（多选↔单选双向，恰 1 条时迁入锚点、多条清空）；**锚点-光标模型**（`m_iSelAnchor`）——Shift 操作 = 锚点..光标区间替换（可扩可缩），非 Shift 变更一律锚点跟随光标。

六控件统一的交互语义：

| 能力 | 语义 |
|---|---|
| Ctrl+点击 | toggle 单项（多选集合增减，重复加/删不重复发事件） |
| Shift+点击 / Shift+方向键 | 锚点..光标区间选择（可扩可缩） |
| 普通点击 / 空白点击 | 替换为单项 / 清除全部选择（Ctrl/Shift+空白不清除，保护多选集） |
| 橡皮筋框选 | 多选态拖动圈选；Ctrl+框选追加而非替换；框选期间选择集实时逐条反馈 |
| ESC | 取消框选，快照还原到拖拽前状态 |
| 键盘导航 | 方向键 / Home / End / PgUp / PgDn 移动光标（六控件均实现 `OnKeyDown`），SPACE toggle，多选态 Ctrl+方向只移光标；焦点光标项绘制焦点框 |
| 事件协议 | 单项事件 `EventItemSelChanged`（`EVT_ITEM_SELCHANGED=15200`）与 `EventTreeItemSelChanged`（`SOUI/include/event/SEvents.h:121`）在条目选中状态真实翻转时逐条触发；锚点事件族（`EventLVSelChanged` 等）只在单选态有效，多选/框选全程不发——避免上层在框选中被重复刷新 |

**demo 与测试覆盖**：`demos/demo` 的七个列表页全部接入运行时"启用多选 / 启用框选"开关（`chk_multi_*`/`chk_band_*` 复选框共 14 处），mclistview 页另有实时"已选 N 项"计数文本（`txt_mclv_selcount`，由单项事件驱动）。`demos/fun_test/test_rubberband.cpp` 以单套件 **37 条**无头用例（`soui_rubberband`）覆盖上表全部语义，含三组易错坐标回归（host 窗口偏移、滚动后内容坐标换算、滚动中 band 并集扩展），规模约占 `soui-headless` 门禁（400 条）的十分之一。边界：band 视觉绘制与边缘自动滚动的定时器 tick 属渲染/消息循环路径，无头测试无法覆盖，以 demo 人工验证补充；语义细节以 `doc/SOUI-列表控件框选多选设计方案.md` 为准。

> **评价**：自绘 DirectUI 的列表控件通常止步于"单选高亮 + 各控件自定义的多选开关"，框选手势一般要应用层自行实现。本框架把"框选手势（`SPanel`）+ 多选状态机（`SViewBase`/各控件）"做成两层框架能力，六个列表控件共享同一套交互语义、事件协议与测试用例——语义一致性由统一测试保证，而非各控件自觉。需要客观记录的是：该能力面仍在收敛期，不同控件家族在多选态锚点角色等实现细节上存在已被设计文档记录的差异；对使用者而言，可观察语义以 `test_rubberband.cpp` 的用例断言为最可靠契约。

**本章要点**：

1. XML + 类 COM 对象工厂使 UI 与逻辑彻底解耦，可视化设计器 `uieditor` 与皮肤热换构成“快速开发”的骨架（§4.1）。
2. 控件面为 39 个内置控件头 + 37 个扩展控件类；六个列表控件共享同一套多选 / 框选 / 键盘导航框架，交互语义由 37 条无头用例锁定，而不是各控件自觉（§4.2）。
3. 该能力面仍在收敛期：不同控件家族在多选态锚点角色等细节上存在已被设计文档记录的差异，对使用者而言，可观察语义以 `test_rubberband.cpp` 的断言为最可靠契约。

## 五、可编程能力：ScriptModule-LUA

第三章考察的是框架自身的工程能力；本章看它的**可编程性延伸**——内置的 Lua 脚本组件。脚本解决的问题是：XML 管布局、C++ 管能力之后，**玩法逻辑、原型验证与频繁调整的胶水代码**不应每次都付 C++ 编译链接的代价。当前状态下，该组件的能力面已与官方 JS 版（soui4js，QuickJS）对齐核心部分，并首次具备**专门的无头测试套件**（§5.5）；`demos/demo` 里的消消乐把这条路径压成了完整的动画型玩法（§5.7）。

### 5.1 设计定位与组件构成

SOUI 的脚本能力是**接口与实现分离**的：`SScriptModule-i.h`（`SOUI/include/interface/SScriptModule-i.h`）定义引擎无关的纯虚接口（加载/执行脚本文件与代码段、对象工厂、事件槽绑定五个入口），具体引擎以 COM 组件形态插入。仓库内置的实现是 `components/ScriptModule-LUA`：

| 构成 | 规模 | 说明 |
|---|---|---|
| 接口层 | `SScriptModule-i.h` 134 行 | 纯虚基类，引擎无关；实现侧 `SScriptModule_Lua` 持有 `lua_State` |
| 模块本体 | `src/`（不含 `exports/`）368 行 | 标识串 `"SOUI.Script.Lua5.4"`（`ScriptModule-Lua.cpp:89`），内核 **Lua 5.4.4**（`third-part/lua-54`，静态链入） |
| 导出面 | `src/exports/` **43 个文件 / 4,200 行** | 约 **1,470 处注册**（类注册 1,361 + 全局函数 109，其中 66 个为事件参数转换 `toStEventXxx`）；38 个 `exp_*` 类绑定 + 5 个基础设施（`toobj.h`/`luaAdapter.h`/`luaFunSlot.h` 等） |
| C++↔Lua 桥 | `lua_tinker/` **3,274 行**（`.h` 2,112 + `.cpp` 1,162） | 对开源 lua_tinker 的 SOUI 定制版（定制点见 §5.4） |
| 组件自带文档 | `doc/` **3 篇 / 873 行** | 导出技术与使用指南、模块升级与踩坑备忘、与 Qt-QML 的对比 |

以上均不含 vendored 的 Lua 5.4 解释器源码。组件自有源码合计 **7,842 行**，占 `components/`（85,082 行）不到一成，按需链接不参与构建时不产生体积代价（§3.2）；其自带文档的完整度在 `components/` 的 16 个组件中最高，是脚本接入的主要参考。

| 环节 | 实现 | 位置 |
|---|---|---|

### 5.3 脚本侧对象模型：ctxId 路由与生命周期三条路径

脚本桥设计里最关键的一处判断是：**Lua 侧持有的 C++ 对象身份在异步回调到达时不可靠**——回调里收到的对象指针每次被重新 push 成新的 userdata（`==` 是裸身份比较，恒不等），且控件可能已被销毁重建、棋子已被回收复用。`ScriptModule-LUA` 的解法是**模板克隆 + ctxId 路由**：

```mermaid
sequenceDiagram
    participant L as Lua 脚本
    participant M as ScriptModule-LUA
    participant W as SWindow(控件)
    participant A as ValueAnimator
    L->>M: ani = LuaValueAnimator()<br/>class_con + constructor_lstate
    L->>M: ani:CopyFrom(模板动画) / SetRangeRect(rc1,rc2)
    L->>M: ani:SetCtx(ctxId) / SetOnUpdate("fn") / SetOnEnd("fn")
    L->>A: ani:Start(浮层窗口) 每个动画单独 Start
    loop 动画帧
        A->>M: onUpdate(ctxId)
        M->>L: 按 ctxId 查表回调 Lua(目标控件指针仅作呈现)
    end
```

脚本回调签名只携带 `ctxId`，Lua 侧凭 id 取回自己的上下文表（动画起点、目标坐标、棋子状态），不依赖任何可能悬空的 C++ 对象身份。`LuaValueAnimator`/`LuaAnimatorGroup` 的 `SetCtx` / `SetOnUpdate` / `SetOnEnd` 即为此设计（`exports/exp_LuaValueAnimator.h:149`、`:159`、`:164`；构造器 `class_con + constructor_lstate` 于 `:275`）。

与其配套的是**释放路径三分法**——导出对象按"谁创建谁释放"分三类，误用会直接导致泄漏或双释放：

| 对象类别 | 入栈方式 | 释放责任 | 典型对象 |
|---|---|---|---|
| 单例 / 宿主 / 窗口树对象 | 普通 push（`ptr2user`，不拥有） | C++ 侧管理，**脚本绝不可 Release** | `GetApp()`、事件参数、窗口树节点 |
| 工厂 new 出的 `IObjRef` 产品 | `class_def` 直绑（初始引用 1） | **脚本必须显式 `:Release()`** | `LoadAnimation`、`CreateTimer`、`SouiFactory` 产品 |
| 生命周期只归属 Lua 的包装对象 | `constructor_lstate` / `push_gcnew`（`val2user`） | GC 直接 `delete`，**脚本绝不可 Release** | `LuaValueAnimator`、`LuaAnimatorGroup` |

> **红线**：同一指针禁止既以托管方式入栈、又以普通 `push` 二次入栈（两条路径的 `__gc` 语义不同）；判据看**继承链**（`TObjRefImpl`/`SObjectImpl` 系）而不是"有没有叫 `Release` 的方法"——普通对象自带同名 `Release()` 时绑定能编译但语义错。此外 `IAnimatorListener` 一类监听器是**非持有的裸指针**（框架不 AddRef、不备份迭代），回调中删除监听器必崩，属脚本契约。

### 5.4 lua_tinker 的 SOUI 定制点

`lua_tinker/`（3,274 行）是脚本桥的地基，针对 SOUI 的接口形态与 lua 调用语义做了八处关键修补（均为当前源码实测）：

| 定制点 | 位置 | 解决的问题 |
|---|---|---|
| 事件字段注册修正 | `exp_eventArgs.h` | `DEF_EVT` 生成 `EventXxx : SEvtArgs + StEventXxx` 多继承，子对象偏移非零 ⇒ 裸指针读字段全部错位；改为注册**完整 `EventXxx` 类**走 `sobj_cast`（63 事件、118 处 `class_mem`），并提供 `toStEventXxx` 别名 |
| `mem_var_derived<T,BASE,V>` | `lua_tinker.h:651` | `class_mem` 用裸指针重解释，派生类注册基类成员变量指针时偏移错位；新增派生类成员绑定（`V BASE::*` 让编译器做偏移调整） |
| 布尔参数 read 修复 | `lua_tinker.h`（read 特化族） | `read<int/BOOL/…>` 走 `lua_tonumber`，而 Lua 对布尔恒返回 0.0 ⇒ **脚本传 `true` 到 C++ 的 BOOL/int 参数一律变 0**（`SetVisible(true)` 实际是隐藏）；全部数值 read 补 `lua_isboolean` 分支 |
| `wchar_t` / `wchar_t*` 绑定 | `lua_tinker.h`（字符串特化族） | 宽字符串原本以 userdata 栈锚定缓冲返回（裸指针读出垃圾）；补自包含 UTF-8↔UTF-16 编解码 ⇒ `CreateChildrenFromXml(LPCWSTR)` 可直接传 Lua string |
| `call<带参>` 错误路径修复 | `lua_tinker.h` | pcall 失败后弹栈顺序错误会偷掉调用方外层栈槽，之后把错误对象当返回值读；5 个重载统一为无条件 pcall + `lua_remove` |
| `push_gcnew` / `constructor_lstate` | `lua_tinker.h:292`、`:1666` | 生命周期完全归属 Lua 的对象入栈助手（`val2user` 语义，`__gc` 直接 delete）；`constructor_lstate<T[,A1..A5]>` 支持 ctor 首参 `lua_State*` 的类直接构造（`LuaValueAnimator`/`LuaAnimatorGroup` 走此路径） |
| x86 `__stdcall` 强转规则 | `exp_ICtrl.h:344` 等 5 处 | 注册 `STDMETHOD` 接口方法时 C 风格强转**必须带 `UAPI`**：剥掉 `__stdcall` 会让重载决议选错 `invoke`（this 走 ECX 而实际是 stdcall thunk），x86 下必崩、x64 单一调用约定不出事 |
| `class_set_cfun` | `exports/toobj.h:47` | 带 `DEF_VAL` 默认参数的接口方法无法直绑，用 cfunction 包装统一支持 |

### 5.5 测试与验证（脚本模块首次进入无头门禁）

脚本模块当前的自动化验证已覆盖到无头门禁层面：`demos/fun_test/test_lua.cpp` 是它的**专门无头测试套件**（**27 条**用例，占 `soui-headless` 门禁 400 条的 6.75%）：

- **两个 fixture**：`soui_lua` 8 条（不创建 `SApplication`，验证模块独立装载路径）+ `soui_lua_app` 19 条（带 app + 资源提供器 + log4z）。
- **驱动方式**：**纯 `IScriptModule` 接口驱动、零 lua 链接**——测试不 `#include` lua 头、不直接调 lua C API，脚本能力只经导出面暴露，因此测的是"脚本看到的 SOUI"而非"实现细节"。
- **成败探针**：`executeScriptFile` 恒返回 TRUE、`executeScriptBuffer` 返回 void，接口层不可靠 ⇒ 用例统一让脚本末尾写 flag 文件，C++ 侧检查文件是否出现（脚本中途 error 则 flag 不出现）。
- **覆盖面**：每个用例对应一个导出对象走完整"创建 → 使用 → 释放 → GC"链路（如 `itimer_release` 专门验证 timer 与事件槽各自的引用计数归属），与 §5.3 的三分法逐条对应；泄漏与 UAF 在 **MSVC Debug（0xDD 填充）+ VLD** 下核查——MinGW release 靠残留字节"侥幸不跑崩"会掩盖 UAF。
- **机制依据**：模块析构执行 `lua_close`，仍存活的 userdata 会逐一收到 `__gc`，这是用例能断言 GC 释放路径的前提。

> ⚠️ **可观测性边界**：lua 错误经模块的 `print_error` 重定向进 SOUI 日志，**app 未装 `LogMgr` 时错误文本被静默丢弃**——无头环境只能靠 flag 文件判成败，调试期需显式装日志管理器。另：该套件与整个 `soui-headless` 门禁一样，**不覆盖渲染与动画视觉**（消消乐的动画正确性仍以人工观察为准，见 §5.7）。

> **工程陷阱的长期登记**：脚本组件要在六端与多种编译配置下工作，历史上踩过并已修复的坑（静态 COM 下 `commgr2.h` 守卫写错导致脚本静默不执行、`EnableScript` 宏门控、x86 `__stdcall` 强转错位、VS2010 x64 `/Og` 误编译 lua 内核 `clearkey`）全部登记在组件自带的《升级记录与踩坑备忘》中，并在其中给出"提交前检查清单"——这是该组件在缺少专职维护者情况下仍能持续演进的保障。

### 5.6 demo 实证①：跑马机（事件 + 定时器 + 动态定位）

`demos/demo` 的脚本页第一个子页是跑马机，UI 全部由 XML 静态声明（4 个 `gifplayer` 赛马、下注金币、终点线），Lua 只负责**数据驱动与定位**：

- `on_init` 逐级 `FindChildByNameA` 缓存赛马/画布对象并建定时器（`CreateSouiFactory → CreateTimer(slot)`，工厂与槽用完即 Release）；
- `on_timer` 以 50ms 定时器每帧读取画布 `GetWindowRect2()`，按随机进度 `Move2()` 平移赛马；`on_canvas_size` 随窗口尺寸重排赛道（`GetDesiredSize` + `Move`）；
- `on_bet` 经 `args:Sender()` → `toSWindow` → 兄弟遍历定位下注目标；跑完后脚本主动 `FireCommand()` 触发按钮命令复用启停逻辑。

验证了脚本在**高频定时器回调**下的基本吞吐与"XML 管布局、Lua 管逻辑"的分工。

### 5.7 demo 实证②：消消乐——纯 Lua 编排的动画流水线

`demos/demo` 第二个子页是一个完整的 8×8 消消乐，逻辑与动画**全部由 Lua 编排**（与跑马机同居 `demos/demo/uires/lua/test.lua`，共 **1,621 行**；页面资源 `uires/xml/page_script.xml`）。它是本章最值得展开的一块——因为它展示的不只是"脚本能挂事件"，而是**用脚本编排一套带状态的动画流水线**。

**场景结构**（`page_script.xml:80`、`:82`）：棋盘 `wnd_xxl_board` 是 `gridlayout`（`columnCount=8`）；棋子为模板实例 `t:g.xxl_ele`（`values/template.xml`，SVG 糖果风，**7 态 stack**，状态切换靠 `SelectPage`）；动画浮层 `wnd_xxl_aniframe` 是**整页 float 覆盖层**（`msgTransparent="1"`，只显示不挡交互），移动副本、消除星芒、飞金币全部画在最顶层；计分/金币用 `t:g.xxl_digit` 七段 LED（10 页 stack，`SelectPage` 驱动翻页）。

**动画资源全部是 XML 声明**（改时长/曲线不改代码）：

| 动画资源 | 参数 | 用途 |
|---|---|---|
| `animator:xxl_move` | `<RectAnimator duration="200" repeatCount="0"/>`（`animator/xxl_move.xml`） | 位移模板；**无插值器** ⇒ `GetFraction()` 即线性进度，脚本据此精确叠加自定义轨迹 |
| `anim:xxl_scale_select` | 500ms 缩放 1→0.8、`repeatMode="reverse"`、无限 | 选中标记脉冲（切换选中前先 `ClearAnimation`） |
| `anim:xxl_fx_pop` | 0.2→1.15（260ms, Decelerate）→ 1.15→1.0（140ms）→ 停留 → 1.0→0.05（300ms, Accelerate） | 消除星芒（三段缩放 + 收缩消失） |
| `anim:xxl_fx_pop_fly` | 同上起手 260+140ms + 200ms alpha 占位 | 金币入账链专用：短停留后即触发 `on_animation_stop` 转入飞行段 |
| `anim:xxl_fx_ring` | 380ms 0.25→1.35 扩张 + 300ms 淡出 | 提示按钮的青色冰环（与金色星芒区分） |

**主链：七步动画状态机**（交换 → 消除 → 下落 → 级联）

① 点击选中（播放缩放脉冲）→ ② 点相邻格，两枚棋子的**浮层副本交叉飞行**（原格子隐藏，副本随动画值 `Move`）→ ③ 交换动画组结束：提交交换数据、扣 1 金币 → ④ 全盘检查，出现 ≥3 连则播聚拢/消除动画组 → ⑤ 组结束启动**下落动画组**（每列被清格子上方的棋子各下落一格）→ ⑥ 组结束计分（连击倍乘）并做数据补位 → ⑦ 再次全盘检查（级联消除）。

每"组"都是 `LuaAnimatorGroup` + `SetOnGroupEnd("xxl_group_end")` + `SetCtx(ctxId)`；**每个子动画必须单独 `Start`**（`SAnimatorGroup` 只聚合回调、不启动子动画——漏 Start 会让组结束永不触发、状态机卡死）。组回调按 ctxId 分发到 `swap / clear / drop / samey / drop_y` 五个分支，**禁用对象身份比较**（原因见 §5.3）。

**金币入账三段链**（动画时序上最精细的一段，纯脚本编排）：

① 消除瞬间在消除中心播短停留星芒（`anim:xxl_fx_pop_fly`，600ms），播完经 `on_animation_stop` 转段 → ② **把这个特效窗口本身**沿抛物线飞到金币数字区：x 线性插值、y 在线性插值上叠加 `arc*4t(1-t)`（弓高 = 飞行距离的 35%，钳制 60~150px），终点缩到 22×22，400ms → ③ 七段 LED 从当前显示值滚到数据值（400ms，按 fraction 取整逐位 `SelectPage`）。**数据层在 ① 起点即 +1，显示层延迟到 ③**；三段用 `ani_count` 计数单位串联（段尾先启动下一段再释放本段，中途不归零就不会打断结算），归零时才跑稳定态结算。

**洗牌动画**：`洗牌`是主动技能（花 5 金币）——Fisher-Yates 受约束置换（保证无初始 3 连且有解），每枚棋子播**两段动画**：第一段以棋盘中心为圆心绕行 1.0~3.0 圈（随机方向），第二段从轨道终点直线飞往目标棋格；棋子落到目标格立即显示新盘数据，全部归位后才检查消除行列；洗牌期间禁用棋盘防误操作。

**稳定性设计（脚本层的自我防御）**：常驻稳定态自检 `xxl_on_settle`——无 3 连且存活动画计数为 0 时，逐格校验"存在 / 可见 / 数据非空"，异常打日志；棋盘重建时把存活动画组移入 orphan 表保活（防 GC 摘掉监听导致副本冻结在浮层上冒充棋子）；动画链进行中拒绝新点击（并发链会捕获中间态、数据与显示分叉后无法自愈）；浮层副本 id 与棋盘/特效分三段 id 空间隔离（防级联时 `FindChildByID` 撞回旧副本导致段错误）；特效窗口由 `on_animation_stop` 自毁，因此多点爆发特效可并发。

> ⚠️ **边界**：动画的视觉与帧时序**属渲染/消息循环路径，无头门禁测不到**，只能人工观察确认；脚本侧的动画契约（包装对象保活、工厂对象显式 `Release`）由 §5.5 的 27 条用例与 VLD 兜底。另需说明：该实现与基于 soui4js 的参考实现（soxxl）逐函数对应，并对参考实现的三处缺陷（副本 id 复用、索引越界、创建失败不回滚）做了刻意修正——这些修正在脚本注释中标注为"勿改回"。

### 5.8 约束与边界（客观面）

- **单线程约束**：`SStringT` 是单线程类型（COW + 非原子引用计数），脚本若在非 UI 线程触达 SOUI 字符串/控件即数据竞争；脚本模型因此是"**脚本逻辑运行在 UI 线程**"，密集计算仍应走 C++ + 工作线程（§6.1、§6.2），脚本只做调度与呈现——消消乐把"每帧级"调用（动画 tick）留在 C++ 侧，Lua 只在组结束回调里提交数据。
- **绑定面即能力边界**：Lua 只能调用 `exports/` 已注册的类与方法，调用未绑定成员（如 `GetParent`）在运行时报错而非静默——写脚本前需对绑定面清单有意识（43 文件、约 1,470 处注册）。
- **默认参数需显式传满**：绑定层 `read` 特化不返回 NULL，缺参会被读成 `0`/空串而不是 C++ 侧默认值——脚本调用二参以上接口方法一律显式传参。
- **组件装载依赖宿主**：脚本组件经 COM 动态装载，要求 `SApplication` 已初始化；脱离宿主进程单独调用组件会在装载期失败。
- **多语言生态的边界**：本仓库内置的脚本组件**仅 Lua**；JS（soui4js）与 Python3（soui4py）是官方独立仓库，且只覆盖 Windows/Linux/macOS 桌面三端——多语言能力不应计入本仓库六端能力（§8.2 风险 10）。当前基线中 Lua 组件的能力面已向 soui4js 对齐（动画体系、矩阵、XML DOM、位图、翻译、日志等导出补齐），多语言间的能力差距正在收窄。
- **性能定性**：脚本适合 UI 胶水、玩法原型与频繁调整的逻辑（demo 两款游戏全程 Lua，`test.lua` 1,621 行）；对帧时间敏感的路径（棋类 AI 搜索、批量绘制）仍在 C++ 层，两者经事件与动画回调衔接。

> **评价**：从"按钮回调"到"带动画状态机的完整游戏"，`ScriptModule-LUA` 的绑定面与机制设计（事件属性直挂、ctxId 动画路由、生命周期三分法）撑起了一条**免编译的玩法迭代路径**；当前基线进一步补齐了导出面（对齐 soui4js）与验证手段（27 条无头用例 + 组件自带三篇文档），使该路径从"能跑"走到"可回归、可交接"。消消乐的动画流水线（§5.7）说明这条路径的上限不止于胶水代码：**多段顺序链、并发特效、抛物线轨迹与滚动计数都能落在脚本里**，而把帧级计算留在 C++ 侧。作为 16 个组件之一，它是"快速开发能力"（§4.1）在逻辑侧的对应物，也符合组件按需装载的体积纪律。

## 六、性能取向与线程协作

工程能力与脚本能力之外，还有一层更底层的取向——**语言与线程模型**。本章先横向对比原生 C++ 与托管原生开发在效率上的差异（6.1），再说明密集计算如何与 UI 线程安全协作（6.2）。

### 6.1 典型对比：SOUI（C++）与 Android/OHOS 原生开发（Java / ArkTS）的效率差异

> **核心论点**：Android 原生 App 的 UI 与业务逻辑跑在 **ART 虚拟机**（Java/Kotlin，托管、带 GC）上，OHOS 原生跑在 **ArkCompiler**（ArkTS/TS，托管、带 GC）上；而 SOUI 整套 UI 树、事件路由、绘制调度、业务代码**全部是 AOT 编译的原生 C++**、无 VM、无 GC。在"用 SOUI 写的应用可与原生开发直接互操作——调系统能力时开发者按原生习惯自写 JNI/NAPI、且运行在 SOUI 的 UI 线程（即宿主原生线程）上、iOS 更可直连 C++"的前提下，SOUI 相对托管语言原生开发获得了**更低延迟、更平滑的帧时序、更小的运行时体积**。
>
> **在"密集计算"负载上，这个差距从"更优"变成"不可替代"**：交互式 UI 的差异是毫秒级抖动，而 CPU 密集型任务（棋盘搜索、路径规划、物理/碰撞、图像处理、加解密与编解码、批量数据计算）的差异是**吞吐与可预测性**——托管语言在这里要同时面对三件事：分配频率高导致 GC 更频繁、并发 GC 的停顿在"多线程 + 大堆"下不可控、以及内存布局被运行时接管（对象头、引用间接、装箱）。C++ 没有三重税：**布局自己定（紧凑 POD / 一维数组）、线程自己分、时间预算自己算**，因此"同样的时间预算能搜到更深一层"。

| 维度 | SOUI（纯 C++） | Android 原生（Java/Kotlin） | OHOS 原生（ArkTS/TS） |
|---|---|---|---|
| 执行模型 | 原生 AOT 机器码，无 VM | ART（AOT+JIT，托管） | ArkCompiler AOT（托管） |
| 内存管理 | 类 COM 引用计数（**确定性回收**） | 分代/并发 GC（**有停顿**） | GC 式托管（**有停顿**） |
| GC 停顿 | **无** | 有，影响帧时序 | 有，影响帧时序 |
| UI 热路径原生边界 | 全程在 C++ 内；仅调系统能力时由开发者自写 JNI/NAPI（同线程），iOS 直连 C++ | 每次调系统 API 多经 JNI 边界 | 每次调系统 API 多经 NAPI 边界 |
| 运行时体积 | 无 VM，轻 | 含 ART 运行时 | 含 ArkCompiler 运行时 |
| 冷启动 | 快（无 VM 预热） | 受 ART 初始化影响 | 受 ArkCompiler 初始化影响 |
| 密集计算（搜索/AI/编解码/图像处理） | 紧凑内存布局 + 自有线程池，多核可跑满、时间可预算 | 分配频率高、并发 GC 停顿在大堆/多线程下不可控，须刻意绕开 GC 才能吃满核 | 同左 |
| 重计算与 UI 的线程协作 | `ITaskLoop` 工作线程池 + `PostTask` 回 UI 线程：一次调用、无锁、无手写消息号（见 §6.2） | `ExecutorService` / `TaskDispatcher` 机制等价，但结果对象仍活在托管堆上 | `TaskPool` 机制等价，同上 |
| 内存安全 | 引用计数大幅缓解，仍需谨慎（外部裸指针/数据竞争） | 托管天然防越界/悬空 | 托管天然防越界/悬空 |
| 生态/SDK 完备度 | 移动 SDK 需自行桥接（门槛高） | 官方 SDK 完备 | 官方 SDK 完备 |

**客观结论（含边界）**：

- **SOUI 的效率优势集中在"应用/UI 逻辑层"，而非像素光栅化**：Android 底层渲染本就是原生 Skia、OHOS 也是原生图形栈，SOUI 在二者之上复用 Skia/Cairo 后端，raster 本身不是差异点；差异来自"UI 树遍历、事件分发、计时器与动画调度、cnchess 这种带棋盘刷新/计时器的对弈逻辑"全部跑在原生 C++ 上，**没有托管堆的 GC 抖动**，帧时序更可控——这对游戏类、实时类应用价值最大。
- **密集计算有可核对的实测样本，不是纸面推论**：`games/cnchess` 的机器人 AI（`algorithm/ChsAIEngine.cpp`，PVS + 空着裁剪 + 迭代加深 + 静态搜索）就是一个纯 CPU 密集负载——搜索深度 3/5/7 三档、时间预算 400/800/1500 ms（`server/config/config.xml`）。它在 C++ 侧的三个关键做法恰好是托管语言最难对位的地方：① **内存布局自己定**——90 格棋盘压成 `int8_t` 一维数组（正红负黑，类型 1..7），Zobrist 键随 `Make/Unmake` **增量**异或维护；② **并行自己分、共享数据无锁**——`thread_local SearchEngine` 让每个池线程各持一份置换表（`2^18 = 262,144` 条 × 16 B ≈ **4 MB/线程**，16 线程上限约 64 MB），线程间零同步；③ **时间自己兜底**——每 4096 个结点查一次预算、到点置 `m_stop` 立即放弃本层（本层结果作废），层间再按 60% 预算软停，从而"到点必返回、且返回的一定是某个完整层的结果"。该引擎只依赖标准 C++ 头（**不依赖 `windows.h`**），因此同一份算法在服务端与各移动端（NDK / OHOS clang）直接复用——**"算得快"与"到处能算"在 C++ 下是同一个文件**。
- **重计算放哪：C++ 只解决"算得快"，SOUI 异步任务解决"算了不卡界面"**：两者是配套的（见 §6.2）。cnchess 的机器人搜索被整体挪到 `ITaskLoop` 工作线程池、只对**棋盘快照**计算，结果再经服务队列串行回到主线程落子——**共享状态始终只有一个线程在写**，业务代码里连一把显式锁都不需要。
- **调系统能力的方式与原生开发一致，不额外强加隔离层**：SOUI 要调摄像头等系统能力时，开发者按原生习惯自己写 JNI（Android）/NAPI（OHOS），调用发生在 SOUI 的 UI 线程（即宿主原生线程）上——**同一线程、无需线程切换、无需重型二次包装**。相较 Qt（线程切换）、Flutter（Platform Channel + 序列化）、Electron（原生 Addon 包装），SOUI 把"调用原生能力"的摩擦压缩到最接近原生开发的程度。
- **必须正视的权衡**：Java/Kotlin 与 ArkTS 在第三方 SDK 完备度、标准库、工具链成熟度、内存安全与迭代速度上显著优于纯 C++；SOUI 的 C++ 路线意味着移动端 SDK 需自行桥接、构建链更重。效率优势不是"全面胜出"，而是**在特定负载（高帧率/低延迟/小运行时）下成立**，且以接受 C++ 生态门槛为代价（脚本化开发支持可部分缓解玩法层的迭代成本，见 §5，但不改变 C++ 主体的门槛）。

### 6.2 密集计算与 UI 线程的协作：SOUI 异步任务

> **论点**：C++ 只解决"算得快"，不解决"算了不卡界面"。SOUI 的两层调度原语把"**重计算放工作线程、结果安全回 UI 线程**"折算成一次 `post` 调用——业务代码里既没有显式锁，也没有手写消息号与手工 `delete` 载荷。

**两层调度原语**：

| 原语 | 位置 | 何时用 |
|---|---|---|
| `IMessageLoop::PostTask(IRunnable*)` | `SOUI/include/interface/SMsgLoop-i.h:152` | 从**任意线程**把任务投到 **UI 线程**执行；入队后 `SMessageLoop` 会 `StartTimer()` 唤醒消息循环 |
| `ITaskLoop::postTask(const IRunnable*, BOOL waitUntilDone, int priority)` | `SOUI/include/interface/STaskLoop-i.h:84` | 把任务投到**专属工作线程**（`components/TaskLoop`，每线程一条队列），返回任务 ID 供取消 |

`STaskHelper::post(...)`（`SOUI/include/helper/SFunctor.hpp:576`）是对上述两者的薄封装：把"对象 + 成员函数 + 参数"（`SFunctor0..9`）或 lambda（`StdRunnable`）绑成 `IRunnable`，按第一个参数是 `IMessageLoop*` 还是 `ITaskLoop*` 自动选路。

**"安全"落在三处契约上（均已回源码核对）**：

1. **载荷归接收方所有**：`SMessageLoop::PostTask` 的实现是 `m_priv->m_runnables.AddTail(runable->clone())`（`SOUI/src/core/SMsgLoop.cpp:257`），`ITaskLoop::postTask` 与 `IWebsocket::postServiceTask`（`components/ws/src/wsServer.cpp:133`，`clone` 于 `:138`）同样先 `clone`——因此投递方在**栈上**构造的 functor 返回后立即析构也不影响执行，**不需要 `new`**。
2. **参数按值绑定**：`SFunctorN` 按值持有各参数、`StdRunnable` 用 `std::bind` 拷贝捕获，发送线程栈上的数据不会被接收方引用；消息载荷用 `std::shared_ptr<std::vector<BYTE>>` 持有，收发线程各自安全。
3. **业务侧无锁**：接收方是某个对象的成员函数，天然只在自己的线程里跑；对共享状态的写入集中在那一个线程内串行发生。

**客户端实例：cnchess 的 WebSocket 主题下载**

数据链路（`games/cnchess/client/`）——网络线程只做拆帧，**完全不碰 UI 对象**：

```cpp

{

    return TRUE;
```

下载本身是一个"带校验的分块传输"状态机（`ThemeDownloadManager::State`：`WAITING_ACK → DOWNLOADING → EXTRACTING → DONE/ERROR`）：先携带**本地缓存 MD5** 发 `THEME_REQ`，服务器回 `THEME_ACK`（服务器 MD5 + 总长；**总长为 0 即表示 MD5 命中、无需下发**），需要时再按 `THEME_DATA`（offset + len）连续分块。收满后 `SaveDownloadedZip()` 做三件"必须做对"的事：按 offset 排序后**校验无缺口、无重叠且恰好覆盖 `[0, totalSize)`**；**增量 MD5**（逐块 `MD5_Update`，不合并成一个大缓冲）；校验通过才写盘并落 `.md5` 文件，最后由 `SResProviderZip` 解压到 `theme_cache/def_theme`。整条链路的**峰值内存只是"分块之和"**，而不是"分块之和 + 一份完整副本"。

> **对照裸 Win32 的等价写法**：要自己 `new` 一个载荷结构、`PostMessage(hwnd, WM_APP+n, wParam, lParam)`、在窗口过程里 `delete`，还要额外处理"窗口先销毁、消息后到"的悬空指针。SOUI 下这一整类样板与陷阱被 `post` 一行吸收。

**服务端实例：机器人 AI 线程池（密集计算 → 主线程落子）**

`games/cnchess/server/RobotAIPool.cpp` 用 `ITaskLoop` 自建上限 1..16 线程的池（当前配置 `robot_ai_pool="4"`），把 §6.1 里的高强度搜索从游戏主线程挪走，同时保证共享状态只有一个线程在写：

- **派发**：`Dispatch(task)` 用 `getTaskCount()` 挑**排队最少**的那个 `ITaskLoop` 投递（`StdRunnable` 捕获一份 `SRobotTask` 副本，做负载均衡）。
- **计算**：`RunTask` 只对 `task.layout` 这份**棋盘深拷贝快照**跑 `CChessAI::SearchBestMove`，绝不触碰实时棋局。
- **回主线程**：结果经 `service` 回调（内部走 `IWebsocket::postServiceTask`，即 LWS 主线程的服务队列，`DrainServiceQueue` 串行排空）回到主线程，由 `ApplyRobotMove` 落子，并校验 `generation` 是否仍等于当前 `m_nChessMsg`——不等即**丢弃过期结果**（悔棋/新局场景）。

**边界与代价（写清楚以免误用）**：① `IMessageLoop::PostTask` 是**纯异步投递、无等待语义**；`ITaskLoop::postTask` 的 `waitUntilDone = TRUE` 才会同步等待（跨线程用信号量），只有在"目标线程反过来等调用线程"的**环形依赖**下才会互等——同线程 + `waitUntilDone` 已被实现短路为直接 inline 执行（`components/TaskLoop/TaskLoop.cpp:69`），不会自锁。② 对象可能先于任务销毁时，用 `cancelTasksForObject(object)` 取消该对象的未执行任务，或按 `postTask` 返回的任务 ID 用 `cancelTask(id)` 取消单个任务（任务循环已停止时 `postTask` 返回 `-1`，不会静默丢任务）。③ 本例中主题的**解压与校验发生在 UI 线程上**——因为进度弹窗需要即时更新、且这是连接成功后的一次性动作；若要把解压也移出 UI 线程，用同一个 `ITaskLoop` 投递即可，机制不变。

## 九、建议路线图（按性价比排序）

1. **补齐移动端 CI**（关闭风险 1）：为 iOS / Android / OHOS 至少加"交叉编译不回归"的 job——不求在 CI 里跑起来，但要保证三端**编译链路不被破坏**；这是当前最高性价比的一项。
2. **在 GitHub 现场核验 Required Checks**（关联 §1.4）：确认 `core-linux-x64` / `core-windows-x64` / `core-macos-arm64` 是否已成为 `master` 的必需检查，避免"写了工作流但没生效"。
3. **按项目需要补齐"迁移面"**（关闭风险 3）：建议优先级为 ①**窗口菜单栏**（`SetMenu`/`GetMenu`/`DrawMenuBar`——弹出菜单机制已完整，缺的是窗口侧挂载）；②**常用原生控件**（`Edit`/`ComboBox`/`ScrollBar`，可沿 `ListBox` 的 Wine 搬运路径）；③**公共控件**与 `InitCommonControls(Ex)`；④**资源对话框**（`DialogBoxParam` 族）。声明层面的 5 项小缺口（`ScrollWindowEx`、`SendNotifyMessage{A,W}`、`SetWindowExtEx`、`SetMenuItemBitmaps`）随调用方出现时顺带补即可。
4. **把 `api_scan` 接入 CI 作为"实现面不得回退"的断言**：把覆盖率从"定期快照"变成"持续门禁"。
5. **脚本绑定面文档化与契约化**（强化优势 14、对冲风险 10）：把 `exports/` 绑定清单（43 文件、约 1,470 处注册）生成 API 参考并纳入文档站——组件已自带三篇文档（含使用指南与踩坑清单）与 27 条生命周期用例，下一步是把"绑定面清单"像 `api_scan` 一样做变更快照，避免脚本生态与绑定实现漂移。
6. **OHOS 无障碍（ACC）按需桥接**（关联风险 4）：桌面三平台已可用；若移动端无障碍成为需求，再为 OHOS 桥接 AT 能力，并解除构建层的强制 OFF。
7. **文档与实现对齐**（关闭风险 9）：cnchess readme 的 `pc_theme/mobile_theme` 描述按实际（下载式主题）修正。
8. **弱化单作者风险**（风险 2）：沉淀 `AGENTS.md`、架构决策记录（ADR）、扩大核心贡献者；当前 `swinx/doc/` 的评估报告体系已朝此方向。

## 十、结论

SOUI4 是一套**工程完成度高、设计自洽**的跨平台 C++ DirectUI 框架。它最稀缺的价值在于：**用 Win32 作为统一的编程世界语，让"为 SOUI 写的 C++ 代码"在六端原生运行，且业务层零平台宏**——`games/cnchess` 的 `__ANDROID__=0`、`__OHOS__=0` 是这一点的硬证据。（注意边界：当前成立的是"用 SOUI 编写的新代码"，**不是"任意既有 Win32 程序直接迁移"**，见 §2.5。）其类 COM 引用计数（`SAutoRefPtr`）与控件树裸指针的配合，在 C++ GUI 内存安全上给出了成熟解；组件化按需装载 + 资源内嵌，使其在**全功能原生 GUI 框架**中体积处于第一梯队；RichEdit / Scintilla 的整体搬运与 RC 资源跨桌面编译，进一步证明 swinx 的兼容策略可复用、可扩展。在开发体验侧，"XML 声明 UI + Lua 脚本逻辑 + C++ 能力层"的三层分工已闭环，且在当前基线中完成了一次能力升级：组件导出面补齐到与 soui4js 对等（43 文件、约 1,470 处注册，覆盖动画体系 / 矩阵 / XML DOM / 位图 / 翻译 / 日志），XML 事件属性直挂 Lua 函数、ctxId 动画路由与生命周期三分法使脚本侧对象管理可判定，并首次有了 **27 条无头生命周期用例**进入门禁。`demos/demo` 的消消乐是这条路径的上限证明——**交换/消除/下落动画组、飞金币抛物线入账链、七段 LED 滚动计分与洗牌绕行动画全部由 Lua 编排**，动画参数则留在 XML 里声明，改玩法不需要 C++ 编译（§5.5、§5.7）。

在性能取向上，选择 C++ 不只是"省一点运行时开销"：**密集计算（棋盘搜索、路径规划、编解码、图像处理这类 CPU-bound 负载）才是 C++ 相对托管语言差距最大、也最难被替代的战场**——内存布局、线程划分与时间预算全部可控，多核才真能被吃满。而 SOUI 的异步任务（`ITaskLoop` 工作线程池 + `IMessageLoop::PostTask` 回 UI 线程）把"重计算放工作线程、结果安全回 UI 线程"的成本压到一次 `post` 调用：`IRunnable` 的引用计数 + `clone` 语义保证投递方栈上对象的生命周期安全，业务侧因此**既不需要显式锁，也不需要手写消息号**。cnchess 的机器人 AI 线程池与 WebSocket 主题下载，分别是"算得快"与"算完安全回到界面"两侧可逐行核对的样本（§6.1、§6.2）。

需要被客观认知的是：上述短板（移动端无自动构建与回归、单作者、swinx 尚未覆盖原生控件库/窗口菜单栏/资源对话框这一"迁移面"、OHOS 无障碍被强制关闭与深度适配待真机验证、多语言脚本生态分仓、vendor 代码占两仓库受控文件约 67.3%，逐条见 §8.2）**性质高度一致——都是"工作量与流程"问题，而非"架构不确定性"问题**：没有一项需要推翻现有设计，全部可用明确的工程投入收敛（§9）。其中补齐移动端 CI 与把 `api_scan` 转为持续门禁，是投入产出比最高的两项。

**总体判断**：SOUI4 适合"以 Win32/WTL 经验、用一套 C++ 覆盖桌面+移动（含鸿蒙）、重视体积与原生渲染"的场景，是当前跨平台 GUI 方案中差异度最高、对 Windows 程序员最友好的一个；其短板可通过明确的工程化投入（移动端 CI、"迁移面"排期、文档对齐、ACC 扩展）在可控成本内收敛。需明确一处能力边界：其"单代码库六端"当前是**为 SOUI 应用**成立的，**把既有 Win32 程序零成本迁移过去尚不成立**（差原生控件库、窗口菜单栏与资源对话框三块，见 §2.5）——该目标在能力上可达，属工作量问题。
